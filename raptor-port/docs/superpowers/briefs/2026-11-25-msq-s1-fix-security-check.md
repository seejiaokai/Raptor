# The S1 fix — the security reader's check of that fix only (chat 187, 25 Nov 26)

Asked of a fresh Opus security reader by chat 187 (the host's reading of D1411: the S1 fix read once more, by the
security reader alone). Plan §19.2, "Its definition — the security reader's S1 fix". Saved whole by the host from the
reader's final reply.

Checked against branch `claude/msq-b1-screens-135` at b154fff98. I changed nothing. The fix is not built yet, so I judged the plan's wording against today's code: `state/units.ts` setGrant/removeGrant, `state/accounts.ts` adminNow/saveAccess/updateAccount/relinkRightsProblem, `state/units-model.ts` levelFrom/adminRoleHolds, `state/perms.ts` unitRowViolation/restoreLeavesOut/adminOwnerViolation/worldsOf and the Plan-left-on-member check, `state/undo-wire.ts` grantCtx/leaveOut/acctLineLeftOut, and `undo/timeline.ts` keptOf/applyRestore.

**Verdict:** the definition closes S1 itself. Two parts of the replay rule are not safe as written (F1, F2), and there are smaller gaps (F3 to F7).

## Findings

**F1 — MEDIUM. The V7 pin "its Undo puts both back" contradicts the definition, and if built it lets a non-149 admin give back Plan of 149.**
- Case: Ranger, 142's own admin with nothing in 149, makes Hunter a member. Hunter's Plan of 149 drops (D2250). Ranger presses Undo. Built to the pin, Hunter's Plan of 149 comes back. That is Plan of 149 given by someone who is neither 149's own admin nor a master admin, which breaks D2626.
- Cause: the V7 pin, "a man made a member by his own squadron's admin loses his Plan row in that command, and its Undo puts both back", clashes with three things: the plan's own rule, which asks `mayGivePlanOf` of every Plan row put back; today's restoreLeavesOut point 4 ("gives back the role only", chat 129, told him); its pin, `piece-b-tables.test.ts` "4. a Plan row put back by one who is not a master admin: left out". A builder satisfying V7 would have to exempt the Undo of a make-member from the check.
- Fix: rewrite the pin as "its Undo gives back the role only; the Plan row comes back only where the one pressing may give Plan of that squadron (its own admin or a master admin)". "Kept, each ruled" (made member, delete, archive) should apply to the forward command and to a replayed removal only, never to a put-back.

**F2 — MEDIUM. Done as a "leave-out", the replay check commits half a step, and the new Plan bell lines then say the opposite of what is true.**
- Case: Kestrel gives Hunter Plan of 149. That one command writes the grant row, Hunter's own account line, and the new admin lines ("Hunter · Given Plan of 149 · Kestrel") to Mako, Saber and 149's other admins. Kestrel then becomes 142's admin holding only Plan of 149, and presses Undo.
- What goes wrong: the grant row is left out, so Hunter keeps Plan; Hunter's own line is left out with it (acctLineLeftOut); the admin lines are not left out — no hook covers the new kinds; the step is therefore not emptied, so it is not refused (timeline keptOf/LEFT_EMPTY) and commits; the gate lets an admin's verified restore take away lines he wrote (adminOwnerViolation, "only taking a line away"). Result: Mako, Saber and 149's admins see the line struck "taken back" while Hunter still holds Plan of 149. Kestrel's Undo list shows the step undone. V7's "his Undo of the give is refused — Hunter still holds Plan" fails.
- The Undo of an end does the same in reverse: "Plan of 149 ended" is struck while Plan stays ended. A Redo would try to put the admin lines back with no grant row changed; S2's new gate rule refuses that, so it fails with the gate's general words, not "left out and says so". The leave-out also half-applies a multi-line Admin → Users Save (for example, Plan of 149 lowered and View of 150 given in one Save).
- Fix (either): preferred — make the replay's Plan check refuse the whole step through the timeline's refusal hook (as masterRightRefusal does), in D148's words, matching the plan's own "A step it stops is refused in today's Undo words"; or extend acctLineLeftOut to the new admin-line kinds, so each line follows the grant row it tells of. Either way, add V7 cases asserting that no "taken back" reaches 149's admins while Plan stands.

**F3 — LOW. The gate never checks the `first` mark on a Plan row.** Once squadrons' own admins write Plan rows, that mark is a way to make someone an admin of a squadron that is not among the seven places. Case: Kestrel forges a give of Plan of 149 to Hunter carrying `first: true`; Viper, 142's other admin, moves Hunter to 149; adminRoleHolds then makes Hunter 149's own admin from the day he arrives — against the K3/K4 promise. The flag is only read in units-model; perms.ts has no check on it (latent today, only masters write Plan rows). Second half: point 2's "with every grant left out, so a Plan of `unit` never counts", read literally, strips adminRoleHolds' `first` path, so a new squadron's named first admin, once moved in, could not give Plan of his own squadron though adminNow says he is its admin (fails closed, against D2626). Fix: the gate refuses `first` on any grant row unless it comes from the master's `unit.add` (or is kept unchanged); define point 2 as levelFrom's home branch with adminRoleHolds unchanged (its `first` path included), only the grant branch left out; a test for each.

**F4 — LOW. An eighth place keeps Plan to a master admin: accounts.ts relinkRightsProblem** ("This sign-in holds a right in 149. Only a master admin can link it to another person." when the right is Plan). A re-link drops every right of the sign-in, so it ends Plan; not among the seven; after the fix it disagrees with the gate and D2626. No hole (the gate's check on the dropped Plan row asks the same rule; the door is stricter). Fix: the door asks `mayGivePlanOf` for each Plan row's squadron, its words follow D2626, a twin in V5.

**F5 — LOW. Point 4 names `w.rowsB` / `w.acctB`, but worldsOf returns null for a command that touches only grant rows** (every setGrant and removeGrant, and a Save with lines only). Built literally with point 5, every own-admin give is refused at the gate (fails closed), or a builder falls back to live rows unsaid. Fix: use the `before` rows and the actor's before-command account that unitRowViolation already builds, or buildWorlds(env).

**F6 — LOW. The receiver's check does not say which rows it reads.** It should read the receiver's role in force on the rows and accounts after the command, as saveAccess already does with `adminNow(next0)`; read on the rows before, Saber's one Save "make Ranger an admin and give him Plan of 149" is refused. The actor's "before" (point 4) must not carry over to the receiver.

**F7 — LOW. The fail-closed list (point 5) leaves out a switched-off account and an archived or deleted man.** adminNow ignores `on` and archived, and the gate reads the session's role; a suspended, archived or posted-out 149 admin whose session has not yet lapsed passes `mayGivePlanOf` (the lapse happens in sessionNow at the next repaint; at the database step the server's gate is all there is). Not new — every admin act has the same window — but cheap to close here: point 5 names these cases too. Today's door fails open with no signed-in account (units.ts `notMaster()` is false when `me` is undefined); point 5 closes it; add "no signed-in account at the door" to V5b or V6.

## Notes, not faults
- Point 1 (master admin) should also require the role in force to be admin, as levelFrom does (the gate's other checks refuse a master viewing as a member anyway).
- The "not covered — NQ1" pin names only the role tick. Two more ways a Plan holder of 149 turns a 149 man into 149's own admin, both covered by D2201, D2336 and D2250: re-linking another 149 admin's sign-in to a 149 member; his Undo of a make-member of a 149 admin. Name them in the pin, so he is shown every way NQ1 happens.
