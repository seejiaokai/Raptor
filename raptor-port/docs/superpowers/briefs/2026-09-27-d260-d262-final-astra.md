## Findings

### 1. High — Roster and event move modes can run simultaneously and one click moves both

Locations: `raptor-port/src/leavewar/ui/Matrix.tsx:3754-3755`, `Matrix.tsx:4401`, `raptor-port/src/leavewar/ui/select.ts:915-923`, `select.ts:976-979`.

Scenario:

1. As admin, open a bid and press **Move**, or drag-select a bid and choose **Move**.
2. While that roster move remains active, click an existing event-row cell.
3. The roster resolver does not recognise the event cell, so the click passes through and opens EventSheet.
4. Press the event sheet’s **Move**.
5. Click a roster day.

What happens: `moveSel` and `eventMoveSel` are both live. Both `wireMove` document listeners accept the roster-day click—`eventMoveDateAt` deliberately accepts roster cells—so the bid and unrelated event both move.

What should happen: exactly one move transaction may be active; starting or interacting with another move surface must not create a second listener/state machine.

Provenance: already present on `9f7814d9`. The base had the unconditional EventRows edit door, independent move states, and an event Move callback that did not clear the roster move. D262 makes the route easier to reach but did not introduce it.

Fix:

1. Replace `moveSel` and `eventMoveSel` with one discriminated state such as `activeMove: {kind:'roster', ...} | {kind:'event', ...} | null`.
2. Mount only the matching `wireMove` effect and banner.
3. Disable/guard EventRows editing while any roster move is active.
4. Make every move entry point explicitly replace or reject an existing active move.
5. Add an integration test: start roster Move → click event → EventSheet must not open; also force event Move after roster Move and prove one target click changes only one object and produces one undo transaction.

### 2. High — Press-drag released off a day lands on the last day crossed

Locations: `raptor-port/src/leavewar/ui/select.ts:890-896`, `select.ts:462-469`.

Scenario:

1. Pick up a bid with **Move**.
2. Press on a day and drag across a valid destination.
3. Continue into the frozen callsign column, heading, or outside the grid.
4. Release there.

What happens: `dragDay` is updated only when hit-testing finds a date. An invalid release leaves the previous valid date cached, and `finish()` commits that stale date. Desktop moves immediately; phone stages the stale date for confirmation.

What should happen: a release that is not currently over a valid day must select nothing—leaving move mode active, or cancelling if the release meets the outside-cancel rule.

Provenance: new with D262’s press-and-drag implementation.

Fix:

1. Keep any cached day only for optional previewing.
2. In `current()`, resolve the current hit and return `null` whenever `elementFromPoint(x, y)` does not resolve to a date.
3. Do not pass the cached preview day as the selection payload.
4. Clear the landing highlight when the pointer leaves valid days.
5. Add mouse and touch tests that cross a valid target and then release over the name column, header, event band, and outside page; assert no `onPick`, no phone Confirm, and unchanged source data.

### 3. Medium — A member’s own award remains hidden and inert before posting-in or after posting-out

Locations: `raptor-port/src/leavewar/ui/Matrix.tsx:503-515`, `Matrix.tsx:543`, `Matrix.tsx:594-601`.

Scenario:

1. As admin, post a person out.
2. Tap a later day, choose **Place leave or OIL here instead**, and grant an OIL award.
3. Close or publish the war.
4. Sign in as that person and tap the awarded day.

What happens: `ownAwardOnly()` is never consulted because `cellOpenable()` is gated by `here`. Since FO/HO has no leave-spending definition, `outLeave` is false. The cell displays `PO` after posting-out—or blank before posting-in—and has no click handler.

What should happen: it should visibly show FO/HO and open the read-only “Your OIL award” sheet at every stage, while retaining the out-of-squadron hatch and exclusion from manning.

Provenance: already present on `9f7814d9`; D261 fixes only in-squadron cells. This remains reproducible with newly created awards, so D56 does not exclude it. `ownaward.test.tsx:17-26` uses only people/dates still inside their squadron range.

Fix:

1. Derive `ownAward` before the display and action gates.
2. For a member viewing their own row, let `ownAward` display the stored FO/HO even when `here` is false.
3. Let that condition call `cellOpenable()` or set `open` independently of `here`.
4. Preserve the current admin precedence: an admin’s out-of-squadron tap should still open the posting sheet first.
5. Add before-PI and after-PO tests at OPEN, CLOSED, and PUBLISHED; assert the owner opens AwardSheet, another member cannot edit it, and manning remains unaffected.

### 4. Medium — Rotating/resizing during Move leaves stale desktop/phone commit semantics

Locations: `raptor-port/src/leavewar/ui/Matrix.tsx:1230-1252`, `Matrix.tsx:1291-1306`, `Matrix.tsx:3125-3132`.

Scenario:

1. Start a move while the viewport is wider than 700px.
2. Rotate or narrow the device below 700px while the move remains active.
3. Tap a destination.

What happens: the installed callback captured the old `phone` value because both effects depend only on their selection state. The tap commits immediately even though the current phone UI requires a staged Confirm. The reverse transition unnecessarily retains phone confirmation on desktop.

What should happen: commit behavior must follow the current form factor, especially because the phone path intentionally prevents an immediate no-undo move.

Provenance: already present on `9f7814d9` for drag-selection and event moves; D262’s one-chip entry point inherits it.

Fix:

1. Mirror `phone` into a ref updated every render.
2. Read that ref inside both `onPick` callbacks instead of the captured value.
3. On a breakpoint transition, clear any staged preview and landing paint.
4. Add breakpoint-change tests in both directions; after desktop→phone, prove the source remains until Confirm.

## Explicit negatives

- D260’s `awardsIn` and removal paths use matching role, date, row, and record gates; member Clear cannot remove an admin award, and schedule-generated credit is excluded.
- One-day Clear, range Clear, and dragged-block Delete reset their confirmation when the selected span changes and name the awards before removal.
- `clearCells` reaches awards beneath both Inputs-owned and war-approved leave, reports a published approved leave that remains, and wraps the operation as one undo gesture.
- The explicit award-specific Remove/Clear doors already identify the record as an OIL award and remain admin-only; they are not silent generic deletes.
- Fill and Move continue to leave awards on their earned dates.
- D261 works for in-squadron own awards at locked stages: AwardSheet exposes no edit/remove controls, while another person’s single-record award remains unopened. Multi-record days continue through the read-only DayList path for members.
- D262 correctly removes the date input, enables one-chip Move, preserves month navigation, disables drag-selection and figure-selection during a move, distinguishes own-day refusal, and keeps refused moves active.
- The 400 ms guard is position-sensitive; deliberate fast clicks elsewhere are accepted.
- Listener/animation cleanup covers click, pointer, context-menu, key, mouse-leave, edge RAF, and the nested gesture machine. Stage, war, history, and Leave-War-screen changes clear both move kinds.
- Mouse-only right-click cancellation and touch long-press handling are correctly separated.
- I read the named unit/E2E coverage but did not launch the app or rerun tests, consistent with the final-read brief. No files were edited.
