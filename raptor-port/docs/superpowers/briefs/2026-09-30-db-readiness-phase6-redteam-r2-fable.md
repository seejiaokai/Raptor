### F1 — HIGH — The whole-day replacement's "stamped with the current fingerprint, not re-made" defeats rule 4: a loaded version's row keeps its old holder (or times) for good, and with the old holder deleted the load door loses the row

**Evidence.** Plan v2 §3 (c), "A whole-day replacement": a version's request row whose request still covers the day "is stamped with its request's current fingerprint (not re-made)". Rule 4 re-makes only when "the request's fingerprint differs from `srcv`". `engine/drafts.ts loadVersionToWorkingCopy` (line 591) and `draftSelect` (line 278) install `liveDay(t.d)` then `leaveOut` → `HOOKS.stripDeleted` (line 102), which is `state/person-delete.ts stripDeletedFromDay` (line 124) — it strips a landed row by the NAME the row carries (`whoId(r.who) === id`, line 132), not by the request's current holder as `engine/overlay.ts hisLanded` (line 93) does. The load then reaches `sched.mutate` through `afterSchedMutate`, so the belt runs after it.

**Scenario.** Setup: Monday published with request R landed, holder A (row `who: A`, `srcv` = fingerprint(A…)). R is handed to B on the Inputs page (live: the belt re-makes the row → B; not saved). Action: "Load onto working copy" of Monday's issued version. Expected: Monday shows B on R's row (the request says B; the version's row is A only because A held it then). Observed under v2: `liveDay` keeps the version's row (`who: A`) and stamps `srcv` = fingerprint(B…) — so the belt's rule 4 reads "matches" and does not re-make; the day row is saved by the load's own command with `who: A`; every later read finds `srcv` current and never re-makes. The pending list reads "whose: A → B" (the input axis) beside a row that still prints A; publish AL1 and the issued programme names A on B's request (D45's principle broken), and the day then reads 0. Variant: delete A first (cutoff before Monday), then load: `stripDeletedFromDay` removes R's row by the name A — B's row is gone from the working copy, though every plain read (`hisLanded`) would have kept it (the exact composition bug Astra 2 closed at the read door, re-opened at the load door). Today's code also brings A's row back but the next edit of R relinks it; v2 makes it permanent.

**Fix — plan first (one sentence of §3 (c)), then build:**
1. §3 (c), whole-day replacement: delete "any other is stamped with its request's current fingerprint (not re-made)". Replace with: every other request row keeps the `srcv` it carries (the version's own, frozen at issue; a plan's, as parked) — the read-time reconciliation that follows (the belt after the load's command, and every later read) re-makes what the request has since changed. Rule 5's stamp stays for a row with NO `srcv` (old data, D56).
2. The load door's strip uses the current-holder rule: export a per-day body from `engine/overlay.ts` (the loop body of `overlayDeletedWeek` — `stripPersonFromDay(d, id, hisLanded(d, id))` for each deleted man whose cutoff ≤ that day's iso) and make `HOOKS.stripDeleted` call it; retire `stripDeletedFromDay`'s own `srcs` derivation (`whoId(r.who) === id`). Keep its return (the callsigns for the message).
3. Tests (red first): the scenario — after the load, the row reads B before and after a reload, the pending list one line; the deleted-A variant — B's row survives the load; `reqonerow`/`drafts` suites unchanged.
