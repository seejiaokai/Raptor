## Finding
1. **Medium — RANGE's `win` cannot tell cause (iii) from Chrome's toolbar simply folding during a flick**, so the report's table would read (iii) on almost every recording. Scrolling down folds Chrome's toolbars and changes the window's height, so RANGE shows e.g. `win 845-874` on a page that never springs or comes loose; the table's row "RANGE win spread by about 29 → (iii) — B or C" then points at cure B or C whatever the cause. Cause: `range.winLo` / `winHi` are updated on every frame; nothing ties a change of `win` to the frames where the page was sprung past its foot. **Fix:** keep a second pair, lowest and highest `win` on frames where `past !== 0`, plus the last frame before `past` left 0; print ` spring win 845-874` or `spring —`; cleared on a page change; say in the file header and the spec's (iii) bullet and table row that (iii) is read from the spring range, the whole-page range also moving when the toolbars fold; a unit test (window 845→874 while past 0 → no spring range; window changes while past > 0 → `spring win 845-874`).

No other findings: the panel's new height (~108) covers only empty page on the pictures; `range.pan` keeps its sign; the foot reading below 0 when the foot was never reached is in the spec's signs paragraph; the phase-1 test's `bottom: '0px'` is consistent.
