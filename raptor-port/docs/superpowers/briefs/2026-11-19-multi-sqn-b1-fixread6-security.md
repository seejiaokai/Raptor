## SEC6-A (highest) — a plain 142 admin can put any bell line on any 149 man's bell, signed with any name, through an ALL AVAIL input (the door fault 2 left open)
- Proof (red): Outlaw made a plain 142 admin; through the app's own command he files an ALL AVAIL input for Jul 20 whose filer field says Osprey (149) while the placeholder's own filer field says Outlaw; in the same command he pushes a line to Osprey with invented words → accepted, in the committed record, on Osprey's bell (expected all three refused). The gate check alone, sent directly, returns no refusal both for a new input and for an existing 142 ALL AVAIL input whose filer Outlaw changes to Osprey; it passes with the line signed `by: 'kes9'` too (posing as 149's admin). Control: the same input naming a 142 man (Ranger) is refused.
- The honest flow has the same fault (red): Hunter (142 admin) files ALL AVAIL on Jul 15, moves to 149 from Jul 16; on Jul 17 his pre-move line about it is still on his bell, and a plain 142 admin's change still tells him (the gate allows it, the pass writes the line) — by D2223 and D2218 he should no longer be told and the old line should have left.
- Cause: `notices.ts filerTold` returns true whenever the input names nobody (`!named.size`); `perms.ts toldBy` asks `filerTold` with `r.by` from the after-image the attacker controls; the input's squadron is judged by the placeholder's filer first (`inputUnitViolation unitsOf`: `ph.by ?? r.by`), so a forged `r.by` does not change the owning squadron; the `toldBy` door checks neither the line's `by` nor its content; `noticeAboutHim` treats such a line as about him, so it never leaves his bell after a move.
- Introduced? No, older: before these commits `toldBy` added `r.by` for every input; fault 2 narrowed it for named inputs and left ALL AVAIL open.
- Fix: (1) in `filerTold`, `if (named.has(f)) return true`; if nothing is named, per image `const ph = placeholderOf(r); const by = ph?.by ?? r.by; const u = by ? homeOn(String(by), inputAtIso(r.date, r.yr)) : null` — told only if `!u`, or `homeOn(f) === u`, or `levelOfAccount(acct, u) === 'admin'`; (2) in `toldBy`, add the filer from the BEFORE image only on a change; on a new input only when `r.by` equals the actor; (3) in `adminOwnerViolation`'s `toldBy` door also require `String(n.by ?? '') === self` (or `n.by == null` for the app's own acts) — the pass always writes the actor as `by`; (4) red tests: the three proofs, plus controls (filer never moved; master filer; named input).

## SEC6-B (introduced by 65950dbfc) — `followUpOf` trusts whatever "taken back" / "again" lines appear inside a genuine Undo or Redo — any number, any content
- Proof (red, two ways): (a) before Kestrel's Undo or Redo, after Osprey's move, crafted lines pushed into the in-memory bell list from the console — in a Redo "again" lines with `d:'deleted'`, 1–31 Aug; in an Undo "taken back" lines with `c:'OIL'`, 1–30 Sep — each naming Osprey's real line by `ref`; swept into the restore's own record (the scheduler store diffs against a lagging baseline), passes the gate, saved. (b) Hooking the list's `push` (on the developer bridge as `window.NOTICES`) while the real follow-up is written: 2 extra "again" and 3 extra "taken back" lines saved; after the Undo Osprey (now 142's) sees all 3 invented "taken back" lines; after the Redo the newest invented "again" ("LL 1–31 Aug deleted again") hides the real one (only the newest "again" of a line shows). Control: the same line as an ordinary command is refused. Before these commits a put in a restore never reached this allowance, so the forged line was refused with the whole restore.
- Cause: `followUpOf` checks only one part of the right kind, its `ref` pointing to a line the restore really replayed, and `to`; not the part's contents against the referenced line, not `name`, `day` or `iid`, not how many follow-ups name one line.
- Fix: (1) rebuild the expected part from the replayed image `was` exactly as `warNoticesReversed` writes it — take-back `{k:'lwback', c:q.c?, a:q.a, b:q.b, d:q.d, ref:x.id, w:q.w?, to:q.to?, tb:q.tb?}`, Redo `{...q, again:true, ref:x.id}` — and require deep-equality with `n.what[0]`; (2) require `n.name === was.name`, `n.day === was.day`, `n.iid === was.iid`, `n.by === self`; (3) at most one follow-up per `ref` per record (a set in `adminOwnerViolation`); (4) better as one body: export a pure `followUpsFor(replayedChanges, dir)` from sync.ts, used by both `warNoticesReversed` and the gate, every non-replayed line the restore puts on another squadron's man required to be one of its results, ids aside; (5) red tests: (a) and (b), the D2222 cases staying green.

## Explicit negatives (checked)
- Forged restores: a command only calling itself `undo.restore`, outside a restore being applied, gets no replay — no follow-up allowance, no put-back; the chat's own D2222 proofs hold.
- Put-back pass: a squadron-business line ("Bidding open/closed") still dropped by `leaveOut`; forced in, it fails `noticeAboutHim` and is refused; the put-back allowance needs `c.before == null` (no overwriting an existing line); a delete in a restore still needs the actor's own line and an exact replay.
- Follow-up limits: to the replayed line's addressee only (`was.to === n.to`), never a third person; none for "Bidding open/closed"; an "again" needs a replayed put, a "taken back" a replayed delete.
- Bell doors: list, unread count, "mark all read", tap — all through `noticeLive` → `noticeLeftBell`; "mark one read" finds the line without `noticeLive` but writes only the reader's own record (no harm); `leaveOut`, the posting take-back and `warNoticesReversed` ask the same rule; storage and the gate's own facts do not go through the display rule.
- Named-input narrowing: a 149 member filer of a 142 man's input refused; a master filer still told (`units-sqn-fixread2` green).

Not proven (not a finding): `noticeAboutHim` reads today's inputs and homes, so a line D2223 retired can come back onto the filer's bell if the named man later moves into the filer's squadron — against D2218's "never brought back"; low harm (his own old line); worth a test.

Ranking: SEC6-A above SEC6-B.
