## What is built

1. **`src/ui/guard.ts` — `guardWords(reason, row, door, to)`** (shape yours; the plan's is `guardWords(reason, door,
   to)`) and what it needs from the table: which lead a row takes. Three rows need more than their id, and get it
   from their own component, never from the page's markup: **`useGuardWork(id, on, say?)` gains an optional third
   argument** — a short value the reporting component hands over with its report and `guard.ts` keeps beside the
   count (cleared with it) — used by exactly: `HolidaysPanel.tsx`'s holiday form (`'new'` | `'changed'` |
   `'noleave'`), `EveryWeekday.tsx` (the window's own title, e.g. `Every Tuesday`), and nothing else. The roll-call's
   R1 scan must still read every report. **"Lying under the Calendar"** for the two settings windows is asked of
   **the Calendar's own full-screen rule** (read how `DaysWindow` / `FloatWindow` decides it fills the screen and
   export that one predicate if it is not already one) — never a second width test of the guard's (§21.1 Q3).
   **"On a page out of sight"** is `row.where !== CURPAGE` for a page row, and for Admin's rows the section shown
   (read how `AdminPage` keeps it — read only; that file is not yours to edit: if the section cannot be read without
   editing it, stop and say so).
2. **`src/ui/toast.ts` — `toastAt(msg, at)` and `placeToast`'s anchored branch, as §4.6 "How `placeToast` learns the
   control" writes them**: the `NoteAt` type; the module `AT`, cleared only by a `toast()` that did not come through
   `toastAt`; inside an open batch a plain `toast`; the anchored place (8px under the bar's foot or the control's,
   the left or right edge from the control, clamped 8px inside the screen, `data-at="ctl"`, the rise-in with no
   sideways shift); **`noteAtFoot(from)` — the one predicate for "a phone" for this note** (the press was inside the
   ☰ menu, or the top bar does not show the squadron picker — read from the app's own rule, `ui/floatwin.ts
   phoneLayout` and the stylesheet's, never a new number); **the ✕ check at every place the note can stand** (one
   constant of the windows' ✕ selectors; a place whose box meets one is passed over for the next — under the
   control, the foot, and only then the top); **the note never covers a control its words name** (§4.6's first
   paragraph: on a phone it stands just above the highest such control, 8px clear, checked again at each new place)
   — each lead names its controls in one table beside the words (Save, Cancel, Add, "Create the … leave period",
   Retry, a window's ✕ — by the selectors the app already has; no new attribute on any component); with the "Not
   saved" band up the note stands under the band, never over Retry; a control not there when the note is raised →
   the foot; the place worked out again only on a window `resize` and when a shell window opens. **The arithmetic of
   "which place" is one pure function of boxes** (the note's size, the screen, the bar's foot, the control's box,
   the ✕ boxes, the named controls' boxes → the place), so jsdom can test it with made-up boxes; `placeToast` only
   measures and applies. Everything else in `toast.ts` — and every ordinary note's place — stays byte for byte.
3. **`src/ui/guardnote.ts` (new)** — the table door → `NoteAt` (§4.6's last bullets: `pick` → `#sqnMenuBtn`, left,
   bar; `toMember` / `toAdmin` → `#roleBadge`, right, bar; `line` → the pressed line inside `.bell-list`; `bell` →
   the bell on screen, right, bar; `card` and `page` → the foot; `undo` is K8's — not here), and the one function
   handed to the seam (`setGuardSay`) that joins the words and raises the note through `toastAt`. With no page (a
