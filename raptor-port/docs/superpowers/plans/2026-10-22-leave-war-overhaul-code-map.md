# Leave War overhaul (D1140–D1207) — the code map

Read-only draft for the build plan, 22 Oct 26, branch `claude/leave-war-overhaul`. Paths are relative to `raptor-port/src`
unless they start `docs/`, `e2e/` (both under `raptor-port/`) or `.claude/`. Nothing is built yet.

**Conventions in the table.** "Stored" names the record in `docs/data-schema.md` §World 2 / `docs/data-model.md` §3 terms
(`lw.war` = LeaveWar period row, `lw.cell`/`rec:` = LeaveBid, `lw.ledger` = LeaveLedger, `lw.opening` = LeaveOpening,
`lw.config` = the ⚙ Setting blob, `notices` = Notice). "Perm" names the `state/perms.ts` COMMAND type and/or the PERMS
matrix row / `ownershipViolation` case, and the `docs/data-model.md` §11 row — the two change together (D200).
A new command type always needs its `perms.ts` row — `leavewar/permsparity.test.ts` pins that every registered type has one.

**Rulings not mapped (no build):** D1140 (the overhaul itself), D1162 (OD stays overseas duty), D1163 (no SC). D1156 is
archived (replaced by D1177). In the D1140–D1207 range but not this overhaul: D1170, D1171 (Tracker bar), D1195 (Remote
Control on handoff). D1179 (Inputs page type filter by family) is filed under `inputs.md` but is overhaul batch 9 — mapped.

## 3. The biggest risks found

1. **D1177 is the load-bearing change and its reach is wide.** ~150 references in 17 source files, ~45 unit test files and
   97 lines of `e2e/leavewar.spec.ts` build or assert a stage. Five behaviours hang on the stage and each needs its new rule
   written down before the build: `canDecide`'s draft refusal; `warEditable`'s "published = finished paperwork" (it gates
   put-back, delete and move of approved leave, and `clashWayOut`); `biddingClosed` as the gate of the dotted "moved" mark
   AND of `doorMoveApproved`'s `tracked` flag; the remarks editor (published only); the member's drag. `measureBidBox` goes
   from one box to one per stretch on the 28k-node grid.
2. **The bell would tell twice.** The war's put-back, delete and move of approved leave already go through the Inputs
   door (`doorWrite` → `writeInputsBatch` → `noticePass`), which skips only a NEW war-approved input — so today a put-back
   already sends "deleted" and a move a "when" line. D1142's lines must replace those for war-approved leave, not add to
   them; and the permission check on notices (`ownershipViolation` 'notices', §11 Notice row) allows only a notice riding
   an input change or the holiday one — a refusal changes no input, so a third writer is needed (D200).
3. **Two new fields on the bid record and one on the OIL award.** `RequestRec` gains `by`/`at` (Approvals' "placed",
   oldest-first) and `docIds` (documents, carried into the Input on approval and back on put-back); the OIL award gains
   `half` (D1164). Each needs the reader in `engine/warrecs.ts`, the row mapping, `data-schema.md` and `data-model.md`
   (D473); the award touches OIL's own rulings (D25, D79–D82, D260).
4. **Grid speed (`docs/performance.md` §E).** Colour by kind (D1175), halves (D1160/D1164) and two entries per cell
   (D1146/D1167) all land in `PersonMonth`, one memo per month, ~28k nodes, an e2e node band of 31,700 with ~7,800 to spare;
   the day panel and the Available offsets must not reach the grid's repaint (FlyRows' memo signature must include the
   offsets or a change will not show).
5. **Permissions that must move together.** New or changed command types: the open-dates writer (replacing `lw.stage`),
   place-and-approve (D1147), the documents writer on a closed date (D1150), the holiday import (D1155), the notices writer
   (D1142), and later D1203's member-written balances (`LeaveOpening` member `R` today, `lw.opening` refused in
   `ownershipViolation`). Each needs its `perms.ts` row and its `data-model.md` §11 row in the same change;
   `permsparity.test.ts` catches a missing command row but not a stale §11 sentence.
