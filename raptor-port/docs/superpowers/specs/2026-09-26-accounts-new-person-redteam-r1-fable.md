## Part 1 — Red team

### Findings, most serious first

**1. The bell's "seen" test is under-specified, and either reading breaks D216 on one width.**
- **Where:** plan §4 ("`UsersPanel` receives `shown` (true when the Users category is the one on screen — on a phone, once he has tapped into it…)"); `AdminPage.tsx` (the page is mounted only while `page === 'admin'` — `Shell.tsx` line 610 — so every visit starts with `cat = 'users'`, `drilled = false`); `scheduler.css` 5951–5955 (the pane is hidden under 821px until `.drilled`; on a desktop the rail and the pane are side by side from the first paint).
- **Failure scenario:** a request is waiting; the admin signs in on a DESKTOP and taps the Admin TAB, not the bell. The Users pane, with the waiting list, is on screen at once, `drilled` still false. If `shown` is read as `drilled`, the effect never runs, the bell stays lit after he has opened the list — D216 broken. If instead `shown` is read as `cat === 'users'`, then on a PHONE the rail alone ("Users · 1 waiting for access") marks the request seen and the bell goes out before he has opened the list — the plan's own §4 says that must not count.
- **Fix to the plan (§4, §5.3):** define it exactly: `shown = cat === 'users' && (drilled || !HOOKS.isPhone())`, computed in `AdminPage` and passed as a prop (the Admin page's breakpoint is 820px, the same as `HOOKS.isPhone` — checked). The seen effect in `UsersPanel` depends on `[shown, version]`. Pin both widths in `accounts-ui.test.tsx` with `HOOKS.isPhone` stubbed: desktop, Admin tab → seen; phone, Admin tab → NOT seen, then drill in → seen. Walk it (Part 2, scenarios 1 and 2).

**2. `ADMINOPEN` is "consumed ONCE" by TWO consumers, and misses the case where the Admin page is already mounted.**
- **Where:** plan §5.3 ("consumed ONCE by the Admin page … and by `UsersPanel`"); `AdminPage.tsx` stays mounted while the page is `admin` and `setPage('admin')` on the same page does not remount it.
- **Failure scenario A:** whichever of the two reads the intent second reads null — if the page clears it after selecting Users, the panel never learns "New person", so the Quals "+ Add person" button lands on Admin → Users with "On the roster" chosen and nothing focused. **Scenario B:** the admin is on Admin → Squadron config when a request arrives (or taps the bell there); `openAdminUsers()` sets the intent and `nav('admin')` changes nothing — the page is already mounted, an initial-state read never re-runs, the category stays on Squadron config and the toast promised a list that is not shown.
- **Fix to the plan (§5.3):** ONE consumer. `ADMINOPEN` carries a nonce (`{ seq, cat: 'users', newPerson?: true }`, `seq` incremented by every `openAdminUsers`, which also calls `notify()`). `AdminPage` alone consumes it in an effect keyed on `ADMINOPEN?.seq`: `setCat('users'); setDrilled(true)` (harmless on a desktop — the CSS ignores it), `setOpenNew(intent.newPerson ? intent.seq : 0)`, then `clearAdminOpen()`. `UsersPanel` takes `openNew` as a PROP and reacts to a change of it (choose New person, scroll the form into view, focus the Callsign/Name box on a desktop). Test: the bell tap while on Squadron config lands on Users; the Quals button pressed twice in a row opens New person both times.

**3. A refusal INSIDE the command is logged as a bug, and the walk watches the console.**
- **Where:** plan §2 (`putNewPerson` "RE-CHECKS `newPersonProblem` there and throws"); `command/commit.ts` `errResult`: a plain `Error` thrown from a reducer prints `console.error('[commit] reducer threw (rolled back)')`; only a `CmdError` (`CmdRefused` is exported) is silent. `accounts.ts` `commitIntent` maps every non-`unauthorized` failure to "That did not save".
- **Failure scenario:** the inner re-check ever fires (two admins' tabs, or the belt-and-braces case the plan built it for) → a bug-shaped console error during the walk (bug-check order §7.2: "Any error during the walk is a finding") and a toast that says "That did not save" instead of the reason.
- **Fix:** throw `new CmdRefused(problem)` from `putNewPerson`; in `commitIntent` (and the new helper's wrapper) return `r.message` when `r.reason === 'refused'`, "You are not allowed to do that" for `unauthorized`, "That did not save" for the rest. Pin: a test forcing the inner refusal asserts no `console.error` and the reason on screen.

**4. The "archived — restore them on the Quals page" refusal names a door that does not exist for the placeholders.**
- **Where:** plan §2 item 3; `people.ts` — `all` and `allavail` are `special: true, archived: true`; `QualsPage.tsx` 827 — the Archived drawer lists `archived && !special`, so ALL / ALL AVAIL can never be restored.
- **Failure scenario:** someone signs up as "ALL" (or the admin types it); approve → New person → the card says "ALL is archived — restore them on the Quals page instead"; the admin goes to Quals and finds nothing to restore.
- **Fix (§2 item 3):** resolve `nameToId(cs)`; if the match is `special` → the plain "… is already taken — callsigns must be unique"; only a match that is `archived && !special` gets the restore wording. Test both.

### Explicit negatives — checked and found sound

- **Atomicity (Q2).** One command enlisting `peopleStore` and `settingsStore` IS all-or-nothing: phase 6 (`commit.ts` 477–480) restores every enlisted store's snapshot — `restorePeople` rebuilds `PEOPLE`, `ID_BY_CS` and the baseline; `restoreSettings` puts every key back and re-runs `accountsLoad` — and discards the deferred effects. `notify()` is latched during a commit (`store.ts` 65 `deferEffect`), so the Leave War's `reprojectRoster` and the Tracker's `peoplewire` (both run on Raptor notify) never see a half-made person; the whole-world guard covers the scheduler store. The people persist is INLINE (`persist.ts` 126 `wbRef.set`), the settings writes go raw while committing (`people-settings-commit.ts` 257–260), and both sit inside the one whiteboard transaction whose savepoint a returned refusal or a reducer throw rolls back (`commit.ts` 235–282, `wirePersist` 139) — so a storage quota error inside the reducer leaves nothing stored. There is no deferred people write that a phase-8 throw could lose. Checked: nothing outside the command reads `PEOPLE` between the mutation and the seal.
- **Permissions (Q3).** Every new type is admin-only by its letters; `cmdAuthorize` refuses member/guest/pending/off at phase 1 before anything runs; `ownershipViolation` would roll back a member's `people/<newid>` and any `settings/accessreqs` change anyway (`perms.ts` 323–351). Nothing in the plan decides a role outside `perms.ts` — `mayManageRoster`, `mayManageAccounts`, `isAdmin` are the only questions asked; reading `SESSION.user` for the seen list is allowed by `perms-scan.test.ts`'s patterns. The §11 edit (`AccessRequest` Admin R U D; the notes) parses under `perms.test.ts`'s parser (letters only, parentheses stripped).
- **The one add (Q5).** The only production writer of a new `PEOPLE[...]` is `QualsPage.tsx` 666 (the others are hydrate/restore/undo-apply, and `renameCallsign` for the index) — the plan's move covers every door. The PID-01 guard as written (`nameToId`: callsign OR bare id, archived and the placeholders included) is carried verbatim; personnel `{ pers: true, q: '', remarks: '' }` and `deriveQuals` are kept; `flight: '-'` matches today's default. Flight keeps a door (the Quals row's flight box, any role on his own row). No e2e test, probe or the Tracker smoke drives the Quals form — only the handpass scripts (finding 6).
- **The bell (Q4).** "Seen" stored on the request, per admin account id, is the right shape: it vanishes with the request when answered (decline, approve, add-account-under-that-name, rename-onto-that-name all remove the request), needs no pruning, survives a reload (`accessreqs` is durable — `CLAUDE.md` §What actually persists), and two admins taking turns in one browser each get their own bell. A member's, a guest's and a pending person's bell never lights (`isAdmin()`), and the guest/waiting/off screens mount no bell at all. A request arriving while the list is on screen is marked seen by the effect re-running on the version tick (given finding 1's deps).
- **Rulings (Q1).** D214, D216, D217, D219, D220, D221, D222, D224 are each read as worded; D204's "a typed callsign never claims a puck" is honoured (never pre-picked; the New person path CREATES a puck, which D214 asks for); D149/D218, D166, D223, D213/D215 untouched; D200/D202 handled in `perms.ts` + §11 together; D56 applied to the old `full` records only. Agent's calls 2–5 are the agent's (the robustness doctrine, D204's reading, the bell's order, no account → no role); call 1 is his (finding 9); call 6 is the existing 26 Aug personnel rule, fine to state (finding 10 is about the silent truncation, not the number).
- **Cross-app seams.** `linkablePeople` lists a roster-only person (no account, not archived, not special) — linkable later. `projectPeople` (`raptorRoster.ts`) keeps ground crew as `pers` with `seat 'gnd'`, so a new personnel person lands in the Personnel group and stays out of manning; a new aircrew person lands by CAT. `projectForTracker` lists aircrew only. `signIn`/`sessionFor` need no change: an approved person signs in at once with any password (`SEED_PASS` is seeds only).
- **The mock-up vs the plan.** Every label, note, button word and order in the four screens matches the eight pictures (sign-up: Displayed callsign/name · Initials · Pilot, WSO or personnel · CAT; approve: On the roster | New person, the two-column pairs, the "Filled from what he gave…" note, Role, "Add person and give access"; add: sign-in first, Person pair, the note, Role, "Add person and account"; the bell toast "1 waiting for access — opening Admin → Users"). The mock's sign-in placeholder "name@mail (blank for someone who will not sign in)" (script line 72) is not in the plan — it is hidden in the pictures because a name is typed; take it or leave it, the note already says it.
- **Gates.** The retired Quals tests (`quals.test.tsx` 360–424) and the geometry test keep working shapes; `rulecheck.mjs` needs NP1–NP8 in `RULES` and each named by a test (the plan says so); `view-reset.test.ts` will not demand a policy for `ADMINOPEN` (it scans exported Set/Map), registering it anyway is right.
