## UNCLEAR items in full

### W6 — with nothing entered, which time does crew rest measure to?
- **Clauses.** D1032 (rule): "the earliest applicable in-time or rally starts its report … for crew rest, OIL and the rest … an empty box's default counts only where no in-time or rally is entered (D592)"; its next sentence: "So OIL and crew rest move only once a time is typed or taken (an empty box's default is today's nominal report, D592)". D1786 moved only "his long day and his Insights hours" to take-off less the default rally, and names nothing about crew rest.
- **Kind:** UNCLEAR (the words can be read as "crew rest counts from the default rally when nothing is entered", or as "crew rest stays where it was until a time is typed").
- **Where:** `engine/validate.ts` crew-rest block, `insOf` = the earlier of the typed in-time and the brief (`e.to − briefLead` when blank); the amber tight-turn advisory (CREW_TIGHT) separately reads `e.to − reportLead`.
- **The exact case.** Sunday: Bane flies VL 18:30–19:30; with the 2-hour debrief his day ends 21:30, so 12 hours' rest clears at 09:30 Monday. Monday: Bane on VL, take-off 12:00, nothing typed in the in-time lines, R or B. The faint R box suggests 09:00 (the default rally); the faint B suggests 09:40. As built: **no crew-rest breach** (measured to 09:40), only the amber tight-turn advisory (measured to 09:00). OIL, the long day and Insights all start his Monday at 09:00. If D1032 means the default rally counts for crew rest too, Monday should carry a red crew-rest breach (09:00 is before 09:30).
- **What he would see:** one red warning or one amber advisory for the same Monday; the day's start for OIL and the long day (09:00) and for crew rest (09:40) differ by 40 minutes.
- **Confidence:** medium that this is a real question — D1786's own row names only the long day and Insights, and the tight-turn advisory looks deliberately built to cover the gap. Settled by asking him: "with nothing typed, should crew rest count from the default rally (red) or stay on the brief with the amber 'tight turn' note (as today)?"
- **Red line seen:** none (as-built pin passes: no CREW_REST, CREW_TIGHT present).
- **Suggested fix if he picks the default rally:** in `insOf`, use `e.to − VCONF.reportLead` where `e.intime` is null (flying legs), and retire CREW_TIGHT's separate nominal reading. Not built.

### W9 — can the "+ In-time" button's Logic words still make a rally?
- **Clauses.** D511 as narrowed by D1026: "the button becomes '+ In-time' and its line is an in-time only; … the word RALLY in this text no longer makes a rally." D1034 (same day, later): "A typed line that still says RALLY stays a rally, as the app reads it today … The build leaves the reading of typed lines unchanged; only the button and the names say 'In-time'." Neither row marks the other.
- **Kind:** UNCLEAR (two live rows, both 19 Oct 26).
- **Where:** `ui/interactions.ts` `[data-itadd]` mints `hh:mmH: ` + `VCONF.reportText`; `engine/reporting.ts` parseReportingLines reads that line like any typed line (RALLY → rally).
- **The exact case.** A squadron sets Logic's "Words the + In-time button fills in" to "RALLY". Wave 1, VL take-off 12:00, VL's R box 10:00. The scheduler presses "+ In-time": the line "09:00H: RALLY" appears. As built, it is a whole-wave rally, which VL's own R box replaces (D505), so VL reports **10:00** (crew rest, OIL, long day from 10:00). Read as D1026 says (an in-time), VL would report **09:00**.
- **What he would see:** an hour's difference in VL's day start, OIL and crew rest, with nothing on screen saying the "+ In-time" line was not taken as an in-time.
- **Confidence:** high that the code follows D1034 (and the existing `ui/intimesadd.test.tsx` "review D2" pins "RALLY" text reading as a rally); which ruling he meant for the button's own words is his. Settled by one question.
- **Red line seen:** none (as-built pin passes: report 10:00).
- **Suggested fix if D1026 governs:** mark the minted line as an in-time (e.g. the parser ignores RALLY in a line equal to the minted prefix + reportText, or the Logic setting refuses the word). Not built.

Later: D1044 "for a SPARE, what counting as a flight changes is its crew rest and its OIL"; D1045 "every row is a jet that flies — SPARE rows included — in the day's flying count and Insights as well as crew rest and OIL"; D1042 "every warning an ordinary flying line gets".
- **Kind:** UNCLEAR (possibly OVERREACH: D1044 names crew rest and OIL as what changes for a SPARE; the SC in-time advisory is not an ordinary flying line's warning).
- **Where:** `engine/validate.ts` SC_INTIME block (fires on any `shift` event with `report < s`); since [STANDBY-FLIES] SPARE rows on a line with B or R typed reach the event stream (`events.ts` buildDay), so the advisory reaches them. As built, Stiff gets the amber "Stiff reports 05:00 for SC AM … cuts into the in-time window before the 07:00 start". By the 24 Aug words, only a MAIN gets it.
- **What he would see:** an extra amber advisory on a SPARE.
- **Confidence:** medium; settled by asking whether a SPARE on a flying standby line gets the in-time advisory. This belongs equally to the standby family (W14–W26).
- **Red line seen:** none (as-built pin passes).
- **Suggested fix if MAIN only stands:** skip SC_INTIME where the event's row is a spare (`saExempt`'s spare test). Not built.
