# Moving a React app into Power Apps

Power Apps code apps (generally available since **5 February 2026**) take an ordinary compiled React + TypeScript + Vite single-page app, host it behind Microsoft's own sign-in inside the Power Apps player, and give it Dataverse and Microsoft 365 connectors through generated TypeScript services — so Raptor's shape (one storage doorway, ~45 tables, React + Vite) fits the platform without moving its 400 files onto Microsoft's starter project. The work splits into three parts: wiring the existing build to Microsoft's tooling (a new npm command-line tool, **`pa`**, which replaced the old `pac code` commands in August 2026), writing one Dataverse adapter behind the doorway, and handing over **source code plus a table list** that the government tenant's IT side rebuilds with their own prefix and publishes themselves. Three facts in the research change the project's plan materially: the player's default **content security policy blocks the app's own `fetch()` of its page-file list and its `blob:` document viewer**; browser storage inside the player is third-party storage that **iPhones may wipe**; and the client library forces every update to "last write wins" (**no ETag concurrency, no batch, no transactions**), while the database — not the app — is the only place a rule can really be enforced, because every call carries the signed-in person's own token. The test tenant must use a sandbox or production environment, not a developer environment, because Microsoft suspends unmanaged developer environments from **15 December 2026** and never lets a security group gate one.

## In plain English, for the owner

A code app is your existing Raptor app, compiled, uploaded into Microsoft's Power Apps, and opened through a Power Apps link. Microsoft does the signing in (the app's own password card goes), Microsoft's database (Dataverse) holds the records, and Microsoft's rules decide who can open it. Nothing about this blocks the move: the app is already built the way Microsoft expects, and every save already passes through one doorway that can be pointed at the database instead of the browser.

Three things the app does today will not work inside Power Apps as it stands. The "download the pages" step and its Retry read a small list file from the app's own folder — Power Apps forbids that by default. The medical-document viewer shows photos and PDFs in a way Power Apps forbids by default. And anything kept only in the browser (the note that reopens the right page after a Retry, folded panels, zoom) can vanish on an iPhone, because inside Power Apps that storage counts as "someone else's" and Safari clears it. Each has a fix on the app's side, or a one-line setting the IT side would have to change for every code app in their environment.

Two things matter for how safe the data is. First, when two schedulers save the same thing at once, the later save simply wins — the platform offers no built-in "someone changed this since you opened it" check, so the app must build its own. Second, because each person's own Microsoft account talks to the database, anyone with access could change records directly, outside the app's screens; the app's own roles only stop honest mistakes. Only the database's own security roles — which the IT side has said they keep to themselves — can truly stop it. That is a question to put back to them.

For the hand-over, the IT side will take the source code and the table list, build the tables with their own short code, and publish the app themselves. Because their short code differs from the test one, the app's link to the tables is regenerated on their side — a planned step, not a fault. If Raptor ever calls a Power Automate flow from the app, that link is known to break when moved to another tenant; a flow that runs on its own schedule is not affected. Your test account needs a proper "sandbox" or "production" environment — Microsoft is switching off the free developer kind from 15 December 2026.

## Code apps are a hosted bundle, a client library and a CLI

Microsoft describes code apps as a way to "bring Power Apps capabilities into custom web apps built in a code‑first IDE": the app is developed locally, published into a Power Platform environment, and gains Entra sign-in, 1,500+ connectors callable from JavaScript, sharing limits, Conditional Access and data-loss-prevention policies ([Overview](https://learn.microsoft.com/en-us/power-apps/developer/code-apps/overview)). At development time there are three pieces: **`power.config.json`** (metadata the CLI and library use for connections and publishing — "Your app logic doesn't need to interact with" it), the client library **`@microsoft/power-apps`**, and the **Power Apps CLI**, whose `pa app push` publishes a compiled app. At run time the **Power Apps host** "manages end-user authentication, app loading, and presenting contextual messages to the user if an app fails to load" ([Architecture](https://learn.microsoft.com/en-us/power-apps/developer/code-apps/architecture)). Only single-page apps are supported; there is no server-side rendering.

The product reached general availability on **5 February 2026** ([Microsoft blog](https://www.microsoft.com/en-us/power-platform/blog/power-apps/generally-available-host-and-run-code-apps-in-power-apps/)). On **18 August 2026** Microsoft rewrote the whole documentation set "for the pa cli GA" ([docs commit](https://github.com/MicrosoftDocs/powerapps-docs/commit/68ec0bdb4e841612073c791871d6ab0c71d7b16f)), and the npm package `@microsoft/power-apps-cli` reached 1.0.0 the next day ([npm](https://registry.npmjs.org/@microsoft/power-apps-cli)). The old `pac code …` group in the Power Platform CLI is still documented but headed "(Preview)… use the npm-based Power Apps CLI instead" ([pac code reference](https://learn.microsoft.com/en-us/power-platform/developer/cli/reference/code)), with no published deprecation date. **Any tutorial, AI answer or internal note older than mid-August 2026 that says `pac auth create`, `pac code init`, `pac code push` or `npx power-apps` is out of date for the commands**, though the concepts carry over.

As read on 19 November 2026 the packages stand at:

| Package | Role | Latest | Notes |
|---|---|---|---|
| `@microsoft/power-apps-cli` | the `pa` command | 1.4.2 (17 Nov 2026) | **requires Node 22 or newer** |
| `@microsoft/power-apps` | client library ("SDK") | 1.6.0 (4 Nov 2026) | 1.1.1+ needed for flows and Dataverse actions |

Sources: [npm CLI](https://registry.npmjs.org/@microsoft/power-apps-cli), [npm library](https://registry.npmjs.org/@microsoft/power-apps), [npm Vite plugin](https://registry.npmjs.org/@microsoft/power-apps-vite). None publishes a changelog or a public source repository, and a community-reported upgrade (SDK 1.1.1 / CLI 1.0.1) removed a generated operation and broke existing apps ([issue #462](https://github.com/microsoft/PowerAppsCodeApps/issues/462)) — so the port should **pin exact versions** and treat each upgrade as a change to be walked.

Every end user needs **Power Apps Premium, pay-as-you-go, an App Pass, or auto-claim** (widened from Premium-only on 23 September 2026), and an admin must switch on **Enable code apps** per environment ([Overview](https://learn.microsoft.com/en-us/power-apps/developer/code-apps/overview)). The documented limitations that matter here: compiled assets are served from a **publicly accessible endpoint with no IP restriction** ("Don't store sensitive user or organizational data in the app"); no Secure Implicit Connections; no Power Platform Git integration; no Power Apps for Windows; Excel Online connectors unsupported ([System configuration](https://learn.microsoft.com/en-us/power-apps/developer/code-apps/system-limits-configuration); [Connect to data](https://learn.microsoft.com/en-us/power-apps/developer/code-apps/how-to/connect-to-data)). A Dataverse-only code app needs **no connector at all**: "Native Dataverse doesn't use a connection ID, connection reference, or dataset" ([CLI reference](https://learn.microsoft.com/en-us/power-apps/developer/code-apps/reference/cli)) — useful in a tenant that allows no outside connectors.

## Eleven commands take the app from a folder to a play link

Microsoft's quickstart starts from a template (`npx degit github:microsoft/PowerAppsCodeApps/templates/vite my-app`), but the template differs from a bare Vite app by only two Power-Apps-specific pieces: the client library as a dependency and the Vite plugin in `vite.config.ts` (`plugins: [react(), powerApps()]` from `@microsoft/power-apps-vite/plugin`) ([template vite.config.ts](https://github.com/microsoft/PowerAppsCodeApps/blob/main/templates/vite/vite.config.ts); [template package.json](https://github.com/microsoft/PowerAppsCodeApps/blob/main/templates/vite/package.json)). There is **no official page for converting an existing Vite app**; the sequence below is assembled from the quickstart, the CLI reference and the template, and the conversion steps are inference by analogy. The plugin's job is undocumented; a practitioner guide says it "handles asset paths automatically", and that without it a custom setup needs `base: './'` or absolute `/assets/` paths break ([Paul Bien guide](https://paulbien.com/guides/code-apps-complete-guide), community). Raptor's `vite.config.ts` already sets `base: './'` (checked in the repo, 19 Nov 2026).

```bash
# 0. Developer PC, once (Node 22+, Git, an IDE)
node --version                                  # must be v22 or newer
npm install --global @microsoft/power-apps-cli  # installs the `pa` command
pa auth login                                   # always opens the system browser; sign in to the TEST tenant
pa auth status                                  # confirm the account; `pa auth switch`, `pa auth logout` (signs out of ALL)

# 1. Wire the existing app (from raptor-port/) — inference from the template
npm install --save-exact @microsoft/power-apps
npm install --save-dev --save-exact @microsoft/power-apps-vite
#   vite.config.ts: import { powerApps } from '@microsoft/power-apps-vite/plugin'; plugins: [react(), powerApps()]
pa app init --display-name "Raptor" --environment-id <environment-guid> \
            --build-path ./dist --file-entry-point index.html --app-url http://localhost:<vite-port>

# 2. Tables — one native Dataverse table per command (script all ~45)
pa app add data-source --connector dataverse --table <prefix>_<table> --org-url https://<org>.crm.dynamics.com
pa app refresh data-source --name <name>        # after any column change; `pa app remove data-source …` to drop

# 3. Run against the real tenant
pa app run                                      # Power Apps local host (port 8080); open the URL labelled "Local Play"

# 4. Publish, share, settings
npm run build
pa app push --solution-id <solution-guid>       # prints the play URL; GUID only, never the solution name
pa app share --principal <emails-or-entra-object-ids> --access play
pa app set-setting --show-header false && pa app push
```

Sources: [Quickstart](https://learn.microsoft.com/en-us/power-apps/developer/code-apps/how-to/create-an-app-from-scratch); [Sign in and manage accounts](https://learn.microsoft.com/en-us/power-apps/developer/code-apps/how-to/sign-in-manage-accounts); [CLI reference](https://learn.microsoft.com/en-us/power-apps/developer/code-apps/reference/cli); [ALM](https://learn.microsoft.com/en-us/power-apps/developer/code-apps/how-to/alm); [System configuration](https://learn.microsoft.com/en-us/power-apps/developer/code-apps/system-limits-configuration).

The defaults matter: `--build-path` defaults to `./dist`, `--file-entry-point` to `index.html`, `--app-type` to `CodeApp` (`MobileApp` exists but is unexplained), and `--app-url` to **`http://localhost:3000`**, saved as `localAppUrl`; the local host itself listens on **8080** (`PA_CLI_PORT`) ([CLI environment variables](https://learn.microsoft.com/en-us/power-apps/developer/code-apps/reference/environment-variables)). Vite's own default is 5173 and Raptor's preview runs on other ports, so `--app-url` must match whatever port the dev server actually uses. Microsoft's pages disagree on whether `pa app run` starts the dev server: the CLI reference says it "Starts the Power Apps local host", while the data and flows pages still say `npm run dev` ([Connect to data](https://learn.microsoft.com/en-us/power-apps/developer/code-apps/how-to/connect-to-data); [Add flows](https://learn.microsoft.com/en-us/power-apps/developer/code-apps/how-to/add-flows)) — run Vite alongside if the Local Play page comes up empty. Local Play must open **"in the same browser profile that you use for your Power Platform tenant"**, and Chrome and Edge "block requests from public origins to local endpoints by default", so a local-network-access permission (or enterprise policy) may be needed — likely enforced by policy on a locked-down government PC ([Quickstart](https://learn.microsoft.com/en-us/power-apps/developer/code-apps/how-to/create-an-app-from-scratch)). Behind a TLS-inspecting corporate proxy the CLI fails with `fetch failed` or `UNABLE_TO_VERIFY_LEAF_SIGNATURE`; Microsoft's fix is to export the corporate root certificate and point `NODE_EXTRA_CA_CERTS` at it, never `NODE_TLS_REJECT_UNAUTHORIZED=0` ([Zscaler issues](https://learn.microsoft.com/en-us/power-apps/developer/code-apps/troubleshoot-zscaler-issues)). A data-source failure is usually a mismatched `environmentId` or a missing `"region": "prod"` in `power.config.json` ([Troubleshoot adding a data source](https://learn.microsoft.com/en-us/power-apps/developer/code-apps/troubleshoot-add-datasource)).

Generated code lands in `src/generated/models/<Name>Model.ts` and `src/generated/services/<Name>Service.ts` ([Connect to Dataverse](https://learn.microsoft.com/en-us/power-apps/developer/code-apps/how-to/connect-to-dataverse)), though Microsoft's pages are inconsistent about the folder (`src/services/` on the flows page). Microsoft publishes **no full schema of `power.config.json`**; its known fields are `environmentId`, `region`, `localAppUrl`, the app type, `appSettings` (`showHeader`, `customizeRequestAccess.{enabled,title ≤100,messageBody ≤1,000}`), data sources with any `@envvar:` references, and flows with their connection references. For pipelines, a service principal publishes with `PA_CLI_USE_SP_AUTH=true`, `PA_CLI_SP_CLIENT_ID`, `PA_CLI_SP_CLIENT_SECRET`, `PA_CLI_SP_TENANT_ID` and `pa app push --non-interactive`, after a maker has run `pa app share --principal <Enterprise-application object id> --access edit` once — the service principal "can't grant itself access" ([Service principal](https://learn.microsoft.com/en-us/power-apps/developer/code-apps/how-to/use-service-principal)). Microsoft also ships a preview agent plugin (`code-apps-preview` in `microsoft/power-platform-skills`) that works in Claude Code; it scaffolds new apps and needs Node 22+ ([plugin](https://github.com/microsoft/power-platform-skills/tree/main/plugins/code-apps)), but nobody reports using it to port a large existing app.

## The player's strict rules break three things Raptor does today

The built files are served from `https://<environment>.powerplatformusercontent.com/` and shown in an iframe of the player at `apps.powerapps.com` ([Embed in an iframe](https://learn.microsoft.com/en-us/power-apps/developer/code-apps/how-to/embed-iframe)). Developers report the frame is **sandboxed**, the path carries a `storageproxy` timestamp that **changes on every push**, the origin root returns RouteNotFound and unknown query parameters are rejected; Microsoft converted the report to a discussion without disputing it ([issue #272](https://github.com/microsoft/PowerAppsCodeApps/issues/272), community). The sandbox flags themselves are undocumented.

**The default content security policy** is enforced since 30 January 2026 ([MC1218747 via aggregator](https://mc.merill.net/message/MC1218747)) and reads ([CSP](https://learn.microsoft.com/en-us/power-apps/developer/code-apps/how-to/content-security-policy)):

| Directive | Default | Directive | Default |
|---|---|---|---|
| `connect-src` | **`'none'`** | `script-src` | `'self' <platform>` (no inline, no eval) |
| `worker-src` | **`'none'`** | `img-src` | `'self' data: <platform>` (**no `blob:`**) |
| `manifest-src` | `'none'` | `style-src` | `'self' 'unsafe-inline'` |
| `form-action` | `'none'` | `font-src` | `'self'` |
| `child-src` | `'none'` | `frame-src` | `'self'` (**no `blob:`**) |
| `frame-ancestors` | `'self' https://*.powerapps.com` | `default-src`, `base-uri` | `'self'` |
| `media-src`, `object-src` | `'self' data:` | | |

Custom values append to a default, but replace a `'none'`. Read against standard CSP rules, three of Raptor's current behaviours collide with this (inference, checked against the repo on 19 Nov 2026). First, the page-download step and its Retry call **`fetch('page-files.json')` and then `fetch` each page file** (`src/ui/pagedownload.ts`); `connect-src 'none'` blocks fetch and XHR **even to the app's own origin**, while lazy chunks loaded by `import()` fall under `script-src 'self'` and should load. The fix is to build the file list into the bundle and let `import()` do the fetching, or ask the IT side to add `'self'` to `connect-src` for the whole environment. Second, the document viewer shows a photo or PDF through **`URL.createObjectURL` in an `<img>` or `<iframe>`** (`src/ui/DocViewer.tsx`); neither `img-src` nor `frame-src` allows `blob:` by default, so medical documents would not display — `data:` URLs for images pass, PDFs need another route, and a developer reports a PDF could not be opened inside a code app at all ([issue list, #413](https://github.com/microsoft/PowerAppsCodeApps/issues?q=is%3Aissue+mobile), community). Third, the CSV export clicks a `blob:` download link (`src/ui/export.ts`); that is a navigation, not a fetch, so CSP does not govern it, but whether the sandbox allows downloads is unknown — walk it. Web fonts must be bundled (Raptor loads none), no Web Workers or service worker (Raptor has none), no web manifest, and the connector and Dataverse calls work under `connect-src 'none'`, apparently because the library talks to the host by message rather than fetch (unconfirmed).

**Static files and versions.** `pa app push` uploads the compiled `dist` as "a new version"; no page covers version history, rollback or deletion ([CLI reference](https://learn.microsoft.com/en-us/power-apps/developer/code-apps/reference/cli)). Because each push lands on a new timestamped path, people still on the old version will request chunks from the old path; whether that path stays live is unknown, so a "page failed to load → reload" fallback — which Raptor's Retry already is — is the right design. No bundle-size, file-count or file-size limit is documented. A binary-corruption-on-upload bug was fixed on 1 July 2026 ([issue list, #389](https://github.com/microsoft/PowerAppsCodeApps/issues?q=is%3Aissue+mobile), community).

**Sign-in.** The host signs the person in with Entra before the app loads, so the app's own login form goes. `getContext()` from `@microsoft/power-apps/app` returns `user.{fullName, objectId, systemUserId, tenantId, userPrincipalName}`, `app.{appId, environmentId, queryParams, dataverseOrgUrl, appUrl}` and `host.sessionId` ([Get context data](https://learn.microsoft.com/en-us/power-apps/developer/code-apps/how-to/retrieve-context)). There is **no token API**; MSAL inside the frame failed because the per-push path cannot be registered as a redirect URI ([issue #272](https://github.com/microsoft/PowerAppsCodeApps/issues/272)). Outside the player `getContext()` never resolves ([recursion.no](https://recursion.no/blogs/preact-power-apps-code-app/), community snippet), and on phones it has timed out after about 8 seconds ([issue #387](https://github.com/microsoft/PowerAppsCodeApps/issues/387)), so start-up needs a timeout and an error state. What happens when the session expires mid-shift is undocumented — leave a phone overnight and tap.

**Routing and deep links.** Microsoft's starter uses React Router's browser history with a base path computed at run time from `new URL(".", location.href)` and rewrites a trailing `/index.html` ([starter router.tsx](https://raw.githubusercontent.com/microsoft/PowerAppsCodeApps/main/templates/starter/src/router.tsx)). Since the host serves only the exact `index.html` path, in-app routes live only inside the frame; **deep links must arrive as query parameters on the play URL** and be read from `getContext().app.queryParams`, as the `DataverseContextRouting` sample does ([samples](https://github.com/microsoft/PowerAppsCodeApps)). A reload of the player starts at the root route.

**Browser storage.** The app's origin differs from the top page's, so its localStorage, sessionStorage and IndexedDB are third-party storage. WebKit — every iPhone browser — **partitions third-party storage and makes it ephemeral** ([WebKit tracking prevention](https://webkit.org/tracking-prevention/)); Chrome and Edge partition but keep it. No issue reports storage throwing inside the player (weak evidence it works). Anything that matters belongs in Dataverse; the browser is a cache that can be empty. The origin stays the same across pushes, so storage that does persist survives a new version.

**Phones, Teams and the header.** The limitation "aren't supported in the Power Apps mobile app" was removed on 29 May 2026; only Power Apps for Windows is listed as unsupported ([docs history](https://github.com/MicrosoftDocs/powerapps-docs/commits/main/powerapps-docs/developer/code-apps)). Microsoft staff fixed an iOS player crash on 15 July 2026 ([issue #373](https://github.com/microsoft/PowerAppsCodeApps/issues/373)), and Android bugs remain open in November 2026 (empty `dataverseOrgUrl` #519, a bridge error blocking connector calls #523, binary transfer #503 — [issues](https://github.com/microsoft/PowerAppsCodeApps/issues)). On Android Chrome the player's `100vh` hides about 71 px under the navigation bar and the app cannot detect it ([issue #364](https://github.com/microsoft/PowerAppsCodeApps/issues/364)). For phones, share the **`/play/e/{env}/app/{app}`** form — the older `/a/` form is intercepted by iOS Universal Links and pushes people into the Power Apps app ([issue #195](https://github.com/microsoft/PowerAppsCodeApps/issues/195)) — with `?hideNavBar=true`, or hide the header for everyone with `pa app set-setting --show-header false` ([System configuration](https://learn.microsoft.com/en-us/power-apps/developer/code-apps/system-limits-configuration)). Page zoom on a phone is governed by the player's own viewport, not the app's (inference), so Raptor's pinch-zoom grids must be walked on a real iPhone. Teams is not mentioned in any Learn page; a Teams tab failed with "refused to connect" and Microsoft called it a CSP `frame-ancestors` issue ([issue #296](https://github.com/microsoft/PowerAppsCodeApps/issues/296)). There is no offline support and no PWA.

**Monitoring.** Health metrics show in the admin center and maker portal; App Insights (or any tool) receives `sessionLoadSummary` and `networkRequest` metrics through `setConfig({ logger: { logMetric } })`, but only once its endpoints are added to `connect-src`, and start-up failures appear only in Power Platform Monitor ([App Insights](https://learn.microsoft.com/en-us/power-apps/developer/code-apps/how-to/set-up-azure-app-insights)).

## Dataverse arrives through generated services with no concurrency guard

Each table's generated service has static `create`, `get(id)`, `getAll(options)`, `update(id, changes)`, `delete(id)` and `getMetadata`, all returning `{ success, data, error?, skipToken?, nextLink?, count?, fileName? }` — failures usually resolve as `success: false` rather than throwing ([Connect to Dataverse](https://learn.microsoft.com/en-us/power-apps/developer/code-apps/how-to/connect-to-dataverse); [library types](https://unpkg.com/@microsoft/power-apps@1.6.0/dist/internal/data/core/types/index.d.ts)). The documented options are `select`, `filter` (OData), `orderBy`, `top`, `skip`, `skipToken`, `maxPageSize`; the library's own typings add `count` (capped at 5,000), `expand`, `apply` and `partitionId`. Microsoft says to always limit columns with `select` and to send only changed properties on update, because "false updates" fire business logic and corrupt auditing. Paging loops `getAll({ …, skipToken })` until no token returns. Lookups are written as `'<schema>@odata.bind': '/<entityset>(<guid>)'` and read back as `_<column>_value` GUIDs ([LOOKUPS.md](https://github.com/microsoft/PowerAppsCodeApps/blob/main/samples/Dataverse/LOOKUPS.md)); multi-select choices need `serializeMultiSelectPicklistFields` / `deserializeMultiSelectPicklistFields` ([helpers](https://unpkg.com/@microsoft/power-apps@1.6.0/dist/data/multiSelectPicklistUtils.d.ts)); file columns take up to 128 MB per upload and image columns up to 30 MB, with file and image support still **preview** ([upload typings](https://unpkg.com/@microsoft/power-apps@1.6.0/dist/internal/data/core/api/uploadRecord.d.ts)). Because the library asks for `odata.include-annotations=*`, choice labels and lookup names should arrive as formatted-value annotations — to verify against a real response before the adapter relies on it. Dates, time zones and currency are covered by no code-apps page; day-level schedule data belongs in "Date only" columns so no time zone can shift a day (inference from general Dataverse behaviour).

What is **not supported**, officially: polymorphic lookups, schema (metadata) changes, **FetchXML** and **alternate keys** ([Connect to Dataverse](https://learn.microsoft.com/en-us/power-apps/developer/code-apps/how-to/connect-to-dataverse)). Dataverse actions, functions and custom APIs now are (`pa app find-dataverse-api`, `pa app add dataverse-api`, library 1.1.1+) ([Add a Dataverse action](https://learn.microsoft.com/en-us/power-apps/developer/code-apps/how-to/add-dataverse-action-function)), and saved views can be run with `retrieveSavedQueryAsync` ([Data.types](https://unpkg.com/@microsoft/power-apps@1.6.0/dist/data/Data.types.d.ts)). What the library itself decides, read from version 1.6.0: **every Dataverse update is sent with `If-Match: *`**, and `updateRecordAsync` takes no ETag — so an update can never be conditional on "unchanged since I read it", and upsert-by-PATCH is impossible ([runtimeDataClient.js](https://unpkg.com/@microsoft/power-apps@1.6.0/dist/internal/data/core/runtimeClient/runtimeDataClient.js)). There is no public `$batch`, transaction or change-tracking (delta token) API; the host batches internally, but not as anything the app controls. Calling the Web API directly with your own `fetch` would need both an admin to open `connect-src` and your own Entra token, which the host does not expose — effectively ruled out in a restricted tenant. These conclusions come from the library code, not from Microsoft's prose, and may change in later versions.

The consequences for Raptor's doorway follow directly (inference). Two schedulers saving the same row both succeed, last write wins; the only atomic server-side guard would be a custom API with a plug-in that compares a version column, and the IT side has said there are no plug-ins or custom APIs, so the app can only narrow the race with its own version column read-compare-write, and must show the person when it lost. A command that writes many rows is many separate requests, so a failure halfway leaves a partial save that the adapter must detect and either finish or undo. Rows must be found by GUID or by `filter`, never by alternate key — which suits Raptor's stable ids if those ids become the Dataverse primary keys. Microsoft's own create sample omits the primary key (`Omit<Accounts,'accountid'>`); whether the generated service accepts a caller-chosen GUID on create — which would make a "fixed id worked out from the natural key" refuse a second copy on its own — is unverified and must be proven in the test tenant.

**Limits.** Dataverse service protection allows, **per user per web server, 6,000 requests and 20 minutes of execution in any five-minute window and 52 concurrent requests**, answered with HTTP 429 and `Retry-After` ([Service protection limits](https://learn.microsoft.com/en-us/power-apps/developer/data-platform/api-limits)); separately a Premium user is entitled to **40,000 Power Platform requests per 24 hours** (6,000 on a Microsoft 365 licence alone), every Dataverse CRUD and connector call counting, batched or not ([Request limits](https://learn.microsoft.com/en-us/power-platform/admin/api-request-limits-allocations)). The library's retry settings are private and undocumented, and `IOperationResult` carries no headers, so the adapter should back off exponentially on `error.status` 429/503/504, cap its own concurrency at a handful of requests (a whole-week publish fired with `Promise.all` could hit the 52-concurrent limit), and never fire a duplicate write. A 30-second change check with a narrow `modifiedon gt <last>` query costs about 960 requests per user in an eight-hour shift — comfortably inside 40,000, provided it pauses while the tab is hidden (inference). Usage reports in the admin center count only Power Automate requests, so Dataverse use cannot be watched there ([Request limits](https://learn.microsoft.com/en-us/power-platform/admin/api-request-limits-allocations)). The default environment includes 3 GB database, 3 GB file and 1 GB log capacity, and a tenant in overage loses environment creation at once ([Capacity](https://learn.microsoft.com/en-us/power-platform/admin/capacity-storage)); file and image columns spend file capacity, auditing spends log capacity.

**Security.** A code app calls Dataverse with the signed-in person's own token (a per-user "dynamic resource token" from the host) ([runtimeDataClient.d.ts](https://unpkg.com/@microsoft/power-apps@1.6.0/dist/internal/data/core/runtimeClient/runtimeDataClient.d.ts)), so **Dataverse security roles are the real enforcement and the app's own roles are a screen-level layer**. Any rule held only in the browser — who may publish, who may edit another man's Quals — can be bypassed by a person who calls the same services from the browser console (inference, but direct: the token and the library are in the page). Microsoft's **Basic User** role covers "core business tables", not custom ones; **App Opener** carries "the minimum privileges to run an app" ([Security roles](https://learn.microsoft.com/en-us/power-platform/admin/security-roles-privileges)), so "basic access" may grant nothing at all on Raptor's tables until the IT side adds a custom role. The natural design for one Entra group is a Dataverse **Entra security-group team** holding that role; membership is read at sign-in and refreshes after eight hours of continuous sign-in ([Group teams](https://learn.microsoft.com/en-us/power-platform/admin/manage-group-teams)). Flows called from the app need end users to hold App Opener "or an equivalent role" ([Add flows](https://learn.microsoft.com/en-us/power-apps/developer/code-apps/how-to/add-flows)).

**Testing.** The package ships `createMockDataExecutor`, but it answers only `retrieveRecordAsync` and `retrieveMultipleRecordsAsync`, ignores filter, sort and paging, and returns `success: false` for every create, update, delete and file call ([mock executor](https://unpkg.com/@microsoft/power-apps@1.6.0/dist/internal/data/core/data/executors/mockDataOperationExecutor.js)); its install hook is not on the public entry point. Real data needs a signed-in Local Play in a browser, which no headless runner can do without stored credentials. Raptor's existing memory and browser backends behind the doorway therefore stay the test backend, the Dataverse adapter is unit-tested against a hand-written fake of the generated services that can return failures and 429s, and the real tables are walked by hand in the test tenant.

## Two tenants, two hand-over routes, and one fragile seam

Code apps are **solution-aware**: `pa app push` places the app in the environment's preferred solution on first publish (else the Default solution), or in `--solution-id <GUID>`, and "When you export the solution from one environment and import it into another, the app moves with it", with Power Platform Pipelines supported ([ALM](https://learn.microsoft.com/en-us/power-apps/developer/code-apps/how-to/alm)). Connection references and `@envvar:` environment variables keep connectors portable ([Connect to data](https://learn.microsoft.com/en-us/power-apps/developer/code-apps/how-to/connect-to-data); [Environment variables](https://learn.microsoft.com/en-us/power-apps/developer/code-apps/how-to/use-environment-variables)). No Microsoft page covers a **cross-tenant** move, managed-solution behaviour for code apps, or whether the target needs "Enable code apps" on before import. Only built output lives in Power Platform; the source repository is the system of record, and practitioners advise deploying "from the repository to Test and Prod" ([Wyatt, DEV](https://dev.to/wyattdave/setting-your-environments-up-for-code-apps-16i8), community).

That leaves two routes. The **solution route** (export a solution from the test tenant, import it into theirs, remap connection references) is the one Microsoft documents, but the IT side takes no solution files. The **source route** is theirs: they clone the hand-over copy, run `npm ci`, `pa auth login`, `pa app init --environment-id <their production environment>` (with `--cloud public` unless their tenant is a US or China sovereign cloud — the CLI accepts `public`, `usgov`, `usgovhigh`, `usgovdod`, `china`), re-add each table against **their** logical names, build, `pa app push --solution-id <their solution>`, and share with their security group. Values that differ per tenant and must not be carried over: environment ID, app ID (minted on the first push in each environment), cloud, Dataverse org URL, solution ID, connection IDs and connection-reference names, environment-variable schema names, and every table and column logical name ([CLI environment variables](https://learn.microsoft.com/en-us/power-apps/developer/code-apps/reference/environment-variables); [CLI reference](https://learn.microsoft.com/en-us/power-apps/developer/code-apps/reference/cli)). The cleanest hand-over ships the source without a populated environment binding in `power.config.json`, plus a script of the 45 `pa app add data-source` commands. The rights the builder needs are not stated by Microsoft for a human publisher; an identity updating an existing app needs "edit access to the code app", and "Environment-level permissions alone don't grant permission to update an existing app" ([Service principal](https://learn.microsoft.com/en-us/power-apps/developer/code-apps/how-to/use-service-principal)). Creating an app needs at least the Environment Maker role and adding it to a solution likely System Customizer (inference) — flag both to the IT side.

**The publisher prefix is in every name.** Generated models and services are produced from live table metadata keyed by **logical name**, which carries the prefix (`talon_person` in test, `<theirs>_person` in production), and queries use column logical names; environment-variable and connection-reference names carry it too ([Connect to Dataverse](https://learn.microsoft.com/en-us/power-apps/developer/code-apps/how-to/connect-to-dataverse)). A different prefix therefore means **regenerating every data source against their tables** and changing every field name the code uses — no Microsoft tool remaps it. The mitigation is one mapping file in the adapter from the app's names to logical names, identical base names, column names, choice numbers and relationships in the table list, so only the prefix differs, and the tables must exist before `pa app add data-source` can run. One community-reported defect bites exactly here: when a lookup column is created through the Web API rather than the maker portal, the generated `@odata.bind` casing can mismatch and `create()` fails ([issue #451](https://github.com/microsoft/PowerAppsCodeApps/issues/451)); the generator also emits `<lookup>name` fields that do not exist ([issue #455](https://github.com/microsoft/PowerAppsCodeApps/issues/455)). If the IT side's kit builds tables by script, every generated lookup must be checked.

**Flows are the fragile seam.** Only solution-aware **instant** flows with the Power Apps trigger can be called from a code app; scheduled and automated flows cannot ([Add flows](https://learn.microsoft.com/en-us/power-apps/developer/code-apps/how-to/add-flows)). An open issue, reproduced on CLI 1.3.0 on 30 October 2026, shows `pa app add flow` cannot bind through a portable connection reference: after a move **to a clean environment in a different tenant, Dataverse calls worked but every flow call failed**, and the only workaround is a maker re-adding each flow interactively per environment; Microsoft has assigned engineers but given no date ([issue #461](https://github.com/microsoft/PowerAppsCodeApps/issues/461)). A scheduled flow owned by a role-based account, running on its own, is outside that defect, but uses its owner's request limits; a flow owned by a service principal draws on a shared tenant pool of 25,000 requests a day unless it carries a Process licence ([Request limits](https://learn.microsoft.com/en-us/power-platform/admin/api-request-limits-allocations)).

**The test tenant must mirror the target.** From **15 November 2026** signing up for the Developer Plan no longer creates a developer environment; unmanaged developer environments are **suspended from 15 December 2026 and deleted from 15 January 2027**; each user may make one managed developer environment, whose users need premium licences ([Developer Plan](https://learn.microsoft.com/en-us/power-platform/developer/plan)). Since a security group cannot gate a developer environment and trial environments do not auto-add group members ([Control user access](https://learn.microsoft.com/en-us/power-platform/admin/control-user-access)), the mirror is a **sandbox (or production) environment with Dataverse**, in the target's geography, Managed Environments on, code apps enabled, the CSP left at its default, a tenant data policy that puts only the Microsoft 365 connectors the target allows in Business and sets the default group to Blocked, one Entra security group on the environment, a "talon" publisher, Dataverse auditing on, and tests run as a licensed non-admin member of the group holding only the custom role — plus a rehearsal of the first push by an account holding only Environment Maker (inference from the cited pages). The US Government admin page does not mention code apps; GCC availability was reported in May 2026 ([discussion #333](https://github.com/microsoft/PowerAppsCodeApps/discussions/333), community) and code apps do not run in China 21Vianet; a non-US government tenant is most likely on the public cloud — confirm with the IT side.

## Conclusion

The research turns the move from a hosting question into a data-integrity question. Hosting is the easy half: the build needs one plugin, one config file and a handful of `pa` commands, and the only runtime surprises — the page-file fetch, the `blob:` viewer, iPhone storage — are local fixes that keep Raptor independent of any environment-wide CSP request the IT side would have to approve. The hard half is that the platform hands the browser a real database token and then offers no concurrency, no transactions and no server-side rules the IT side will let Raptor own; the app's roles and its version checks become courtesy, not control. Before the database step, the decisive questions to put to the IT side are therefore what "basic access" grants on custom tables, whether a scheduler group can get a second, wider role, and whether one custom API for guarded saves would ever be allowed.

The hand-over route the IT side chose — source plus table list, rebuilt under their prefix — is actually the more robust of the two Microsoft-era options, because it sidesteps the undocumented cross-tenant solution import and the flow-binding defect, at the cost of regenerating every data source. Keeping app-called flows out of Raptor, putting all logical names behind one mapping file, and moving the test tenant onto a sandbox before 15 December 2026 are the three cheapest actions that remove the largest known risks.
