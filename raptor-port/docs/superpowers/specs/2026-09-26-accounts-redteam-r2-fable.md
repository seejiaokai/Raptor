# Red-team report — `[ACCOUNTS]` plan, round 2 (Fable 5.1, 26 Sep 26)

Read of the revised plan (commit 468e31cd) with both round-1 reports, the rulings named in the brief, and the code the revisions touch. Read-only; nothing edited.

**Verdict at the top: APPROVE, on condition that findings 1–3 are written into §4.3 before build step 1 starts.** All three are corrections to the contents of the `COMMAND_OPS` mapping and one named command; none changes a module, a test file, a screen or a build step, so the plan's shape holds. The rest are build-time details.

## Findings

**1. MAJOR. "`COMMAND_OPS` maps EVERY registered command type" is not what §4.3 then describes: it names only three registration sites and misses twenty registered types.** The Leave War registers eight types as `anyone` (`raptor-port/src/leavewar/state/store.ts:1157-1160`: `lw.edit`, `lw.decide`, `lw.move`, `lw.ack`, `lw.approve`, `lw.decideApproved`, `lw.removeApproved`, `lw.moveApproved`) and the Tracker registers twelve (`src/tracker/app/core.js:394-399`: eleven `trk.<collection>` types and `trk.gesture`). §4.3 says the registrations in `sched-commit.ts`, `people-settings-commit.ts` and the undo timeline call `cmdCheck(t)`; those two files are not named, so a builder following the text leaves them `anyone`, and the coverage test either enumerates only the three files (green while `lw.edit` is open to every actor) or enumerates the registry (red forever). The plan's own line "refused for guest, pending, off: every forward command" (§4.3) is then false for the Leave War and the Tracker, and the §11 rows for `LeaveWar`, `LeaveBid`, `LeaveLedger` and the Tracker tables have no gate mapping at all.
Scenario: a pending or guest actor reaches any Leave War writer (a stale listener, a future call site); the writer's own `canEditRow` runs with viewer `''` and refuses `setCell`, but `advanceStage`, `setManualCredit` and `grantTo` are gated by `state.role`, which `resetSession` sets to `member` for every non-admin session (`src/state/store.ts:327`), and the command gate says `anyone`. Expected under the plan: refused at the gate for any non-member.
Fix, in §4.3 and build step 1:
- Add the two registration sites to the list that calls `cmdCheck(t)`. Map `lw.edit`, `lw.move`, `lw.ack` → member-and-admin (authority at the writer: `canEditRow` with the viewer, `canDecide`), `lw.decide`, `lw.approve`, `lw.decideApproved`, `lw.removeApproved`, `lw.moveApproved` → admin only; every `trk.*` type and `trk.gesture` → member-and-admin (D121: everyone edits the Tracker; guests, pending and off refused).
- The coverage test enumerates the registry itself, not three files: export a `registeredTypes()` from `src/command/permissions.ts` beside `hasPermission` and assert every entry has a `COMMAND_OPS` row and every row names an op in `PERMS`.
- `cmdCheck(t)` must return ONE function object per type (a memo map), because `definePermission` throws on a conflicting re-register (`permissions.ts:37-41`); today's `anyone` is a shared constant so re-registration is silent.

**2. MAJOR. The four board-write types are left member-and-admin on a premise the code does not support, and the "write functions" the plan points at have no role check.** §4.3 puts `sched.slot`, `sched.fill`, `sched.text`, `sched.delete` under "member-and-admin, gated at the write function" because "a member's own input can land a row on a published day's working copy… those cascades run through these types". They do not: an input's landing runs inside the `inputs.write` / `inputs.batch` command (`src/state/store.ts:148-177`, the inputgate apply), and any command raised inside a running command child-joins with no re-authorization (`src/command/commit.ts:355-363`; `permissions.ts:9-12`), so an admin-only gate on the four cannot break any cascade. Meanwhile the functions that open them (`writeSlot`, `writeFill`, `writeText`, `writeDelete`, `store.ts:74-106`; `textedit.ts:55`) carry no role check; the only gate is the board's render-time `canEditSched`. This is the 6 Aug 26 rule (page AND write path) left unmet on the scheduler's own writes.
Scenario: member session, a stale delegated handler or hand-made call reaches `writeSlot`; `sched.slot` commits and the working copy changes under a member's name. Expected: unauthorized at the gate.
Fix: map the four to `mayEditSched()` (admin only). Keep `sched.mutate` member-and-admin (it is the backstop that input epilogues can fire outside a command). Keep `inputs.write` and `inputs.batch` member-and-admin, and add `meta.owner` to `inputs.write` from `commitNewInput`, `commitInputEdit`, `removeInput`, `setInpField`, `setLeaveRemarks` (`src/ui/inputedit.tsx:797, 905, 1275, 1310, 448`): the check refuses a member when `meta.owner` is present and is not his person; with no meta the writer's own check stands (so `w.fileInput`, `caldrag.ts:76` and the LW absence door keep working). Red first: a member actor committing `sched.slot` is refused.

**3. MAJOR. `settings.accessreqs` "open for pending" grants a pending principal a whole-table write, not "create his own request".** Every `store.set` outside a command opens `settings.<key>` with no meta (`src/state/people-settings-commit.ts:239-242`), so the gate for a pending actor authorizes replacing the entire list. §11 will say the PENDING principal may create his own request; the gate as mapped says he may delete everyone's. IT translates the table; the app's gate must mean the same thing.
Scenario: pending session; any code path calls `store.set('accessreqs', [])`; the command commits, every waiting request vanishes and the Admin badge clears.
Fix: `requestAccess()` in `accounts.ts` opens its own named command `access.request` that enlists `settingsStore`, appends exactly one entry built from `SESSION.name`, and throws `CmdRefused` if one already exists; inside it `store.set` writes raw because the hook is inert while committing (`:240`). `COMMAND_OPS`: `access.request` → pending only; `settings.accessreqs` → admin only like every other key. Do the same for the admin's approve (`account.approve`: add the account and clear the request in ONE command, so the pair rolls back together — Astra R1-10 point 6 asked for this and the disposition says accepted, but §6/§7 never state that approve is one command). Tests: pending actor on `settings.accessreqs` → unauthorized; `access.request` twice → refused; a failed approve leaves both keys unchanged.

**4. MINOR. The source scan's patterns and allow-list do not match the forms the code uses, so it either stays red on files the plan never lists or is loosened until it catches nothing.** The plan's patterns are `SESSION.role`, `LOGINROLE`, `=== ME` / `!== ME`, `.role === 'admin'`. There are 140 role comparisons across 28 files; the Leave War UI alone has forty (`leavewar/ui/Matrix.tsx` 29, `Chrome.tsx` 6, `DayList.tsx` 4, one each in `SelectSheet`, `CounterSheet`, `OilTracker`, `ManningSheet`), reading the LW store's `role`/`viewer` props in the forms `role !== 'admin'` and `viewer === p.id` (`Matrix.tsx:570-576`), and it is neither allow-listed (the plan allows "the Leave War's own store and engine") nor on the rewrite list. `sync.ts:1393` and `QualsPage.tsx:470` read `SESSION.role !== 'admin'`; `undo/timeline.ts:349-351` and `command/permissions.ts:27,32` read `.role === 'admin'` legitimately.
Fix: (a) regex patterns: `\bSESSION\.role\b`, `\bLOGINROLE\b`, `\bME\s*(===|!==)|(===|!==)\s*ME\b`, `\.role\s*(===|!==)\s*'(admin|member|main)'`; (b) allow-list adds `command/permissions.ts`, `undo/timeline.ts` (or move `mayReverse` into `perms`), and the `leavewar/` tree with the stated reason that its `role`/`viewer` are written only by `resetSession` (the seam) and proved by the parity test; (c) `sync.ts:1393` and `QualsPage.tsx:470` become `mayManageRoster()`; (d) the scan is red on today's tree and green only after step 7.

**5. MINOR. `people.edit` own-or-admin checks `meta.owner` against the actor, never against what changed.** `updatePerson(pid, change)` runs an opaque closure; the gate authorizes in phase 1 before apply (`commit.ts:242`), so a closure that touches a second row commits under a valid owner. Fix: inside `updatePerson`, after `change()` and before persist, diff `PEOPLE` against the people baseline and throw `CmdRefused` if any id other than `pid` changed (the store already keeps the baseline, `people-settings-commit.ts:128-129`). One test: a change writing two rows rolls back. This is Fable R1-4's "every changed `people/<id>` equals the actor's person", closed cheaply.

**6. MINOR. The lock-out fallback replaces the whole list with the seeds.** §1: when no enabled admin with an existing person remains, "the seeds are the in-memory answer" — every real account disappears from memory, and the first admin edit writes the seed list over storage. Fix: keep the cleaned list and add the seed admin `ad` to it when its name and person are free; test: a stored list of two members and no admin loads as those two plus `ad`.

**7. MINOR. `endUndoSession` must clear the seq maps with the entries.** `resolveRoot` walks `causedBy` through `bySeq` and `rootOfSeq` (`undo/timeline.ts:157-175`); `_resetTimeline` clears both (`:632-639`). If only `entries` is emptied, a projection caused by a pre-sign-in command folds into an entry that is no longer listed. State that `bySeq` and `rootOfSeq` are cleared, `expected` and `barrier` are kept (D148's conflict detection rides `expected`). Test: commit as A, sign out, sign in as B, a projection caused by A's seq arrives; nothing throws and nothing is undoable.

**8. MINOR. `resetPopsForSession` has no mechanism that keeps its "one list" complete.** `pops.ts` holds fourteen flags (`DAYPOP`, `INSIGHTS`, `AIRKEY`, `TPLEDIT`, `WAVEEDIT`, `DAYTPLEDIT`, `DRAFTSEDIT`, `INPEDIT`, `OILASK`, `DOCVIEW`, `DRAWER`, `WEEKCAL`, `HISTLIST` with `HISTGROUP`/`HISTOPEN`); the plan lists some and writes "…". Fix: a `POPS_RESET` registry beside the flags, mirroring `VIEW_RESET` (`state/view.ts:780`), and a test that every `export let` in `pops.ts` has an entry, so a new window cannot be missed. `SBDAY`, `AVAILWIN`, `SECDEFOFFER` are already swept by `resetSession` (`store.ts:290-305`).

**9. MINOR. The non-local-host test must name the Tracker's own hooks.** `src/tracker/app/core.js:6021-6034` installs `window.__coreForTests`, `__fileFormatForTests`, `__fileStoreForTests`, `__markDirtyForTests`, `__undoForTests` on every host, and `__coreForTests` carries writers (`applyCharts`, `applyStudents`, `migrateAllCourses`). Not an escalation (D121: everyone edits the Tracker; a guest never mounts it), but roll-call 38 says "the whole bridge", and a test asserting "every bridge name is absent" must either gate these too or list them as out of scope with the reason.
