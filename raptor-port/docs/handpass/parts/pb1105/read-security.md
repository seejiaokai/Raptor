# Security read — [POSTOUT-RUN-NOTICE] (890964ac7..HEAD, raptor-port/src), 5 Nov 26

**Summary:** one real hole, new with this change: an Overseas Sqn or SANS posting pass now always takes the scheduler's records with it and never first puts them back to what is saved. So a change made in a browser console (a member's, in his own browser, where the pass runs) is saved as the app's own act and passes the gate: another man's input, a schedule day, or a forged bell line to anyone. The new notice check also lets a `po` line through with the wrong outcome, the wrong `to` or any `at`/`iid`/`day`, and lets any other line with no named maker through. The members' own doors are tight. The read side is tight. §11 does not mention the new writer.

Method: read the diff; read `postingPassViolation`, `ownershipViolation`, `cmdAuthorize`, `schedStore`/`tellPass`, `runPoOutcomes` and its triggers; ran a throwaway probe test (deleted afterwards, no tracked file changed) on the production doors: the admin posts a man out, the member `us` (Ranger) signs in, the date arrives, the console pushes two forged notices and edits another man's input, then `runPoOutcomes()`. Ran `npx vitest run src/state/perms.test.ts src/state/perms-scan.test.ts`: 2 files, 94 tests passed.

## Findings

### 1. (High, new with this change) A console change to the scheduler's world rides the posting pass, saved as the app, unchecked
- **Steps:** (a) an admin posts a man out to Overseas Sqn or SANS with a date. (b) On or after that date, a member signs in on his own browser. Each browser runs its own pass, at boot and on every notify (`sync.ts` ~2778/2794/2815), under the system actor. (c) Before the pass runs (or with `poDone` not yet set), the member's console changes memory: `NOTICES.push({id:'x',to:'casper',by:null,…,what:[{k:'lw',…,d:'approved'}]})`, edits or empties another man's `INPUTS` row, or edits `DAYS`. (d) The pass runs. Probe result for **sans** and **overseas**: one `lw.postoutRun` envelope, actor `system`, carrying `inputs/<another man's input>`, `notices/nforge1` (a forged "leave approved" line to Outlaw) and `notices/nforge2` (a forged `po` line). `ownershipViolation` returned **null**, so the command is kept. For **delete**, the forged changes were swallowed: that path resyncs first.
- **Cause:** `src/leavewar/sync.ts` `runPoOutcomes`, in the apply: `if (needsDays) resyncSchedBaseline()` is still gated on a Delete, but the enlist became unconditional (`txn.enlist(schedStore)`, "the scheduler store too, every time"). The scheduler store diffs a lagging baseline against the live world (`sched-commit.ts` `capture: baseline()`, `records` decomposes `histSnap`, which includes inputs, days, the book, plan and notices). So every stray in-memory difference becomes this command's change. Before this change a non-delete pass did not enlist the scheduler store, so nothing rode. The gate does not catch it: `perms.ts` `ownershipViolation` runs only `postingPassViolation` for the system actor, and that checks `lw.postouts`, `people`, `settings` and `notices` and nothing else. `inputs`, `days` and `sched.*` from the pass go unasked (and `COMMAND_OPS['lw.postoutRun']` names Input D/U and ScheduleDay U, so the future database rule as written would allow them too).
- **Fix (both parts):**
  1. `src/leavewar/sync.ts` `runPoOutcomes`: put the scheduler's world back before enlisting, as the roster is. Change `if (needsDays) resyncSchedBaseline()` to `if (own || needsDays) resyncSchedBaseline()`. This is what the Delete path already does: the stray change is never saved. Better still, mirror `revertUnsavedPeople`: add `revertUnsavedSched()` in `sched-commit.ts` (`if (!schedBaselineClean()) histRestore(baseline())`) and call it `if (own)` before the enlist, so memory is put back as well as left unsaved.
  2. `src/state/perms.ts` `postingPassViolation`: refuse by collection, not only by the four it knows. Track `const anyDelete = [...posted.values()].includes('delete')`. Refuse every change whose collection is not `lw.postouts`, `people`, `settings`, `notices` or the Leave War profile rows the outcomes write, unless `anyDelete` and the collection is one a Delete writes (`inputs`, `days`, `sched.*`, `amendment` — take the exact list from `applyDelete`'s envelope). With the pass on the server at the database step, this is the rule the service account's changeset must meet, so it belongs in the gate and in §11 (finding 3).

### 2. (Medium; reachable today only through finding 1, but it is the database's rule) The new notice check holds who the line is about, and little else
`perms.ts` `postingPassViolation`, the notices loop: it requires a new row (`before == null`) with `by == null`. A `po` line must name a posted man and hold one part. Not checked, each accepted by the gate in the probe or by reading:
- **`o` against the outcome posted.** A SANS posting can carry a line saying "Posted out · deleted" (the probe's `nforge2`, `o:'delete'` on a SANS or overseas pass, passed). Admins are told a man was deleted when he was not. `acct` is not tied to Overseas either.
- **`to`.** Any id: a member, the posted man himself, an archived man, or no one. A `po` line to a member is hidden in his session (`noticeLive` → `mayEditSched()`), so it does not show. But it is a stored row addressed to him, and at the database step his read rule ("`to` = me") returns it, naming another man's posting. That is a leak of information he could not see before. The `noticeLive` hiding is a screen check, not a security one.
- **`at`** (back-dated, which drops it below the bell's 30 shown, or future-dated, which pins it on top), **`iid`** (any input id, not `''`), **`day`** (any date, not the posting's), **`name`**, extra fields, and **several lines for one admin about one man**.
- **Any line with no named maker that is not `po`.** A `lw`/`lwopen`/`lwback`/`oilhol` line, or any input line, to anyone, in any pass. Those are the Leave War lines a member's command may never carry (`WAR_LINE_KINDS`). The comment says these are "the lines a Delete's inputs owe", but nothing ties them to a Delete or to an input this changeset changes. A `po` part in a later position (`what[1]`) is not checked either.
- **Fix** (in the same loop): keep `posted` as id → `{ outcome, date }` (the date is already worked out there). For every notice change: refuse unless `c.op==='put' && c.before==null`, `n.by==null`, and the keys are a subset of `id,to,by,at,iid,name,day,what`. Then:
  - If `what` holds a `po` part anywhere: `what.length===1`; `posted.get(who)` exists; `p.o === outcome`; `p.acct` only when outcome is `overseas`; `n.iid===''`; `n.day === date`; `String(n.to) !== who`; `n.to` is the person of an admin account that is on, read from the account rows as this changeset leaves them, or from the accounts list the gate can read; `Math.abs(n.at - Date.now()) <= STAMP_SKEW_MS`; at most one such line per `(to, who)`.
  - Otherwise: allowed only when `anyDelete`, with no `WAR_LINE_KINDS` part, and `n.iid` names an `inputs` change in this same envelope (the `rides` test the member case uses).

### 3. (Low — records) §11 and the table description do not name the new writer (D200: perms.ts changes together with §11)
`perms.test.ts` and `perms-scan.test.ts` pass (94 tests). They compare `COMMAND_OPS`/`PERMS` with the table, not the prose, so they cannot see this gap. `git diff 890964ac7..HEAD -- raptor-port/docs` touches nothing.
- `raptor-port/docs/data-model.md` §11, the `Notice` row (~line 1560), lists three writers (input change, holiday, admin Leave War command). Add a fourth: "the posting pass on its date — the app's own, `by` empty — writes one `po` line to each admin who can sign in, about a man that same changeset posts out, with that posting's outcome and date; a posting made today writes it inside the admin's `lw.postout`; no member's command ever carries one (`perms.ts` `WAR_LINE_KINDS`, `postingPassViolation`)".
- The posting-pass paragraph (~line 1588), "In one changeset it may change only …", should add those `Notice` rows and the Delete's schedule and input rows (finding 1 fix 2).
- The `### Notice` section (~line 996) needs a fourth kind: `po`, `input` empty, `day` the posting date, `what` `{k:'po', who, o, acct?}`, and the derived "off the manpower" line that is never stored. `data-schema.md` §The bell's notices should list the `po` part too.

## Answers to the five questions
1. **Member / guest / a "restore":** no. A member's `put` of a line with a `po` part (any position) is refused (`warLine` uses `.some`). Rewriting needs `before == null`. Deleting needs `origin==='restore'` and `b.by === him`, and a `po` line has `by` null. Guest, pending and switched-off accounts change nothing. Calling a command a restore gains nothing here. An admin's own command is unrestricted, as for every notice: that is by design and unchanged. The admin's `lw.postout` adding Notice C does not widen anything, since a member already fails its Profile U `never`.
2. **Console → pass:** yes. That is finding 1, new with this change. The check is not tight: finding 2.
3. **Seeing more:** the stored lines go only to `schedulerIds()` (admin, account on, tied to a person) through `noticePosting`'s `here()`. A posted-out admin is not told. A member session never lists a `po` line (`noticeLive`). The only way a member's row gets one is a forged `to` (finding 2), which the database read rule would then serve him.
4. **The derived line:** `postedLines` returns nothing unless the asking person is in `schedulerIds()`, and `noticeLive` hides it in a member view or session. Nothing leaks.
5. **§11:** yes, the prose needs changing: finding 3. The permission tests pass.

## Notes
- The pass runs in every signed-in browser, a member's included, and each browser runs its own against its own store. That is why finding 1 is reachable today. `data-model.md` already says the pass moves to the server at the database step. Fix 2 of finding 1 is what that server rule must hold.
- `UsersPanel.tsx` interpolates the line's `who` into a CSS selector (`[data-person="${ringPid}"]`). Today `who` is an app-minted person id, so it is safe. Wrapping it in `CSS.escape(ringPid)` costs nothing and stops a malformed id from throwing inside the Admin page's effect.
- `openNotice` opens Admin → Users for whoever taps a `po` line. A member cannot list one, and the Admin page renders a member as a member anyway, so this opens nothing new.
- The probe's storage in the unit setup writes only account rows, so "was it stored" was read from the committed command (the stream plus a gate pass). In the app, the row writer saves from exactly those changes.
- Not a finding (D56): nothing here lives only in stored demo data. Finding 1 hurts new data going forward.
