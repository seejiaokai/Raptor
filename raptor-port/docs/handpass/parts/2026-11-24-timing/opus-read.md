## Findings (appended as confirmed)

### F1 — With the readout open, Escape on the open scheduler board folds the readout and leaves the board open (breaks "Escape closes what opened last", D2112) — CONFIRMED by a failing test

- **Setup:** a computer (wider than 620px), the address with `?timing`, so the readout opens by itself at the start (D2483). Sign in as an admin, go to Edit Schedule, open a day's board (the day's title button).
- **Action:** with the keyboard nowhere (or on one of the board's buttons), press Escape.
- **What shows:** the timing readout folds to its corner button; the board stays open. A second Escape closes the board.
- **What should:** the board — opened last — closes; the readout, opened at the start, stays as it was (one press, one thing, the newest thing: D641/D2112, the design guide §2).
- **Cause:**
  - `src/ui/boardescape.ts` line 31, `OVER` includes `.floatwin:not([hidden])`; `overBoard()` (line 34-40) returns true whenever ANY movable window is in the page, so `boardEscapeWants` (line 44) answers '' — the board never closes while the readout is open, whatever else is going on.
  - `src/ui/FloatWindow.tsx` line 195 (`if (forward(id)) notify()` at mount) makes the readout the front window (`frontWin()==='timing'`) the moment it opens by itself, and line 229 then lets its Escape listener close it on any Escape that is not typed in a box. The readout stays "front" for the life of the page whenever no other movable window is up (`winorder.ts gone()` line 38 hands front back to the last one in `UP`, which is the readout).
  - The same front-window state is read by `InputsCal.tsx` 203/609, `SansCal.tsx` 240 and `floatwin.ts makeEscWaits` (line 51): each stands aside while another window is front, so a readout that ever becomes front (it does at mount and on any press on it) can take Escape away from those too.
- **Fix, step by step:**
  1. `src/ui/FloatWindow.tsx`: add an optional prop `bystander?: boolean` to `FloatWin` ("a window that opened by itself, for the developer: it never joins the window order and answers Escape only with the keys inside it").
  2. In the mount layout effect (lines 192-209): when `bystander`, do NOT call `forward(id)`/`notify()`, do NOT call `n.focus(...)`, and in its cleanup do NOT call `gone(id)` (leave the opener-refocus as is).
  3. In `onPointerDownCapture` (line 261): when `bystander`, return without `forward(id)`.
  4. In the Escape listener (lines 228-242): replace the `frontWin() !== id` test, when `bystander`, with "the keyboard is inside THIS window": `const at = document.activeElement; if (bystander) { if (!el.current || !at || !el.current.contains(at)) return } else if (frontWin() !== id) return` (keep `e.defaultPrevented` first).
  5. Render `data-bystander=""` on the window's root div when `bystander`.
  6. `src/ui/boardescape.ts` line 31: change `.floatwin:not([hidden])` to `.floatwin:not([hidden]):not([data-bystander])`; and in `boardEscapeWants` (after the `t && t.nodeType === 1` guard, before the TYPING test) add `if (t.closest('.floatwin')) return ''` so an Escape pressed with the keys inside the readout (or any window) stays that window's.
  7. `src/ui/TimingReadout.tsx` line 256: pass `bystander: true` to `FloatWin`. The caret-restore effect (lines 240-243) can then go, since a bystander window no longer takes the keyboard as it opens — but keep a pill-opened window taking the keys: pass `bystander: true` only for the window's FIRST open (`startOpen` and not yet folded), or add a separate `noFocus` prop for that; either is fine, the board rule is the point.
  8. Add the proof test below to `src/ui/` (named e.g. `timing-escape.test.tsx`), red before step 6, green after.
- **Proof (ran, saw fail):** `scratchpad/reads/opus-proof/zz-proof-board-escape.test.tsx` — the real `App`, signed in as admin, Edit Schedule, the readout mounted in its own root as `timingwindow.tsx` does (startOpen), the board opened on day 2, Escape with the keys nowhere. Expected `{ boardOpen: false, readoutOpen: true }`, received `{ boardOpen: true, readoutOpen: false }`.
- **Browser input for the host:** desktop 1366×768, `/?timing`, sign in as the admin, Edit Schedule, press a day's title to open its board, click an empty part of the board's bar (keys on nothing), press Escape once: today the readout folds and the board stays.

### F2 (low) — A page change made while the tab is ALREADY hidden is timed across the hidden spell (a row of tens of seconds) — CONFIRMED by a failing test

- **Setup:** `?timing`, signed in as an admin, on Edit Schedule; the tab hidden (another tab or window in front).
- **Action:** a page change made by the app itself while hidden — e.g. the account check in `ui/App.tsx` (lines 37-46) running on a timer-driven repaint and calling `refreshAccess` (`state/store.ts` 548-553), which moves an admin who has just become a member from Edit Schedule to View-only Sched; he comes back within two minutes.
- **What shows:** a row "View-only Sched · opened before · 40.0 s" (the hidden spell counted as the page's time).
- **What should:** no row — a wait the tab was hidden for is dropped (F9's own rule, `timing.ts` head and line 776-781).
- **Cause:** `src/ui/timing.ts` 776-781 drops only a wait that was RUNNING when the tab went hidden (`visibilitychange` → `pageGen++`); a mark made while already hidden starts a fresh wait (`timePage`, 727-734) whose first frame only comes when the tab is shown again, and `GIVE_UP_MS` (120 s) is the only bound.
- **Fix, step by step:** in `timingMark` (`timing.ts` 750), after `markTap?.(m)` and before the `boot`/`first` line, add: `if ((m.kind === 'page' || m.kind === 'signin') && typeof document !== 'undefined' && document.visibilityState === 'hidden') { pageGen++; signinGen++; return }` (a sign-in cannot be pressed in a hidden tab; the page case is the one that matters). Add the proof test to `timing-watch.test.ts` under "F9: a hidden tab".
- **Proof (ran, saw fail):** `scratchpad/reads/opus-proof/zz-proof-hidden-mark.test.ts` — hidden, then the page mark, then visible 40 s later and three frames: expected no page row, received `{ page: 'viewsched', first: false, ms: 40040 }`.

### F4 — With the readout open, ONE Escape on Edit Schedule with a seat picked both puts the seat down AND folds the readout (one press, two things — D2112) — CONFIRMED by a failing test (same cause and fix as F1)

- **Setup:** a computer, `?timing` (readout open from the start), signed in as an admin, Edit Schedule, a seat picked (pressed, so it is armed for a name).
- **Action:** Escape, the keyboard on nothing.
- **What shows:** the seat is put down and the readout folds to its corner button, on the same press.
- **What should:** the seat is put down; the readout stays (one press, one thing; the seat was picked after the readout opened).
- **Cause:** `src/ui/textedit.ts` 547-548 puts the armed seat down without marking the key used (no `preventDefault`), as it always has; the readout's Escape listener (`src/ui/FloatWindow.tsx` 228-242, on the window, heard after the document's) then finds the key unused and `frontWin()==='timing'` (set at its mount, line 195), so it closes too. Before this branch no movable window was up on Edit Schedule at the start, so the gap never showed; the readout is up on every computer from the start.
- **Fix:** F1's steps 1-4 (a `bystander` window answers Escape only with the keyboard inside it, and never becomes the front window by itself). Optionally also add `e.preventDefault()` beside `view.disarmSlot()` in `textedit.ts` 548 — but check `escwindows.test.tsx` 139 / 296 first, which pin the ALL AVAIL window's order around a picked seat.
- **Proof (ran, saw fail):** `scratchpad/reads/opus-proof/zz-proof-arm-escape.test.tsx` — the real `App`, admin, Edit Schedule, the readout mounted open in its own root, `view.armSlot('d:2.0.0')`, Escape on the page: expected `{ seatDown: true, readoutOpen: true }`, received `{ seatDown: true, readoutOpen: false }`.
- **Browser input for the host:** desktop, `/?timing`, admin, Edit Schedule, press an empty seat on a day so it is picked (ringed), click an empty part of the page, press Escape once: the ring goes AND the readout folds.

F4, a further instance (by reading, the same mechanism — for the host to run): the bell's list closes itself on Escape without marking the key used (`src/ui/topbits.tsx` 77, a document listener), so with the readout open, one Escape with the bell's list open closes the list AND folds the readout. Browser input: desktop, `/?timing`, admin, any page, press the bell, press Escape once — the list closes and the readout folds. F1's fix covers it.

## Smaller notes (no failing test; for the host's judgement)

- **"Sign-in shown" is not measured to the same end as the pages.** The `first` mark is taken in a passive effect (`main.tsx` 30-36), not two frames after the card is on screen as the plan's script measures "open the app → the sign-in card". The row can read a frame or two earlier than the plan's figure it will be compared with. To make them comparable: in `timing.ts` `timingMark`, for `first`, emit inside two `rafFn` calls with `t: now()` taken there.
- **A refused or waiting sign-in starts a sign-in wait** (`Login.tsx` 28-30 marks every kind but `bad`: `off`, `waiting`, `new` too). Normally harmless (no week; the wait ends at 120 s). Only if he is let in within those two minutes (approval in the same browser, demo only) would a row include the wait for approval. Tidy fix: mark only when `r.kind === 'ok'`.
- **"First time" can be a page already built in the background.** On a computer the Leave War is built hidden two seconds after the last keystroke following sign-in (`Shell.tsx` 126-169), and a first open abandoned mid-download leaves it built too; either way the next open reads "Leave War · first time" with no download. - **A readout arriving after the sign-in takes the keyboard** for a moment (`FloatWindow.tsx` 196) and hands it back only in a later effect (`TimingReadout.tsx` 241-243); if the keyboard was nowhere it stays in the readout. Only on a weak signal where its own small download lands after the sign-in. F1's `bystander` (no focus at mount) removes it.
