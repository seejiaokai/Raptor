## Scenario design: member and guest writes. Read-only, nothing changed.

I read the code but ran nothing. Every scenario below is about something that should exist and may not. Line numbers are from this worktree. "Storage" means the app's saved data in the browser (the whiteboard). In every scenario, check it before and after the action.

### What I found by reading (useful for sizing the walk)
- **The failed-save warning has gaps.** It is drawn only by the main app's top bar (`Shell.tsx:398`) and the full-screen surfaces (`SchedBoard.tsx:718`). The sign-in screen, the access screens and the guest app draw nothing, and `App.tsx:54-57` routes those sessions away from Shell. The saver's failed state also outlives a sign-out: `logout.ts:10-14` never asks the saver, and `postman.ts` has no reset.
- **Saves can happen while a guest, pending or suspended person is signed in.**
  - The pending person's own access request goes through the saver (`accounts.ts:425-440`, `access.request`).
  - The app's own passes run as the system actor, which the permission check never stops. The Leave War sync runs on every app redraw (`leavewar/sync.ts:2738-2751`). It runs the posting pass (`runPoOutcomes`, `sync.ts:2275-2307`, saved as `lw.postoutRun`) and the OIL pass (saved as one `lw.sync`, `leavewar/state/store.ts:1718-1744`). A guest's week tap (`GuestApp.tsx` → `loadWeek` + redraw) is such a redraw.
- **"Publish AL#" on the Amendments panel has no role check.** `ALPanel.tsx:59-62` enables the button when the day is signed off. Its click throws away the command's result. The command gate refuses a member (`commit.ts:261`), and the command layer shows no message for that refusal. So a member's press does nothing and says nothing — the 1 Oct finding is still there. The day-head Publish day / Publish AL / Unpublish buttons are not drawn for a member (`html.ts:1663, 1680`; sign-off strip `html.ts:1818`; `editMode` at `store.ts:823`). Their click handlers also return silently (`interactions.ts:1433, 1443, 1459`).
- **The admin's member-view switch does not close open windows.** `switchRoleView` (`store.ts:500-513`) leaves Edit Schedule and Admin and drops the armed seat and Logic editing. It does not close windows: the input window, the ALL AVAIL window, the Days window, the changes window, or the Leave War and Tracker sheets. Only a sign-in or sign-out closes those (`pops.ts:176-213`, session scope only).
- **A refusal reads like a fault.** `sched-commit.ts:663` turns every refusal into "Couldn't save that — try again", including a refusal because of the person's role.
- **`?fresh=1` is honoured on any host.** `storage/boot.ts:66` gives a memory-only store, and so does browser storage that cannot be touched (`:69-75`). The save status then always reads "saved", but nothing is kept.

### Ranked scenarios

1. **The access request fails to save, and the screen still says it was sent.** Setup: storage that refuses writes (localStorage full, or a backend whose save always fails); sign in as an unknown name. Action: fill the Request access form and press Request access. Expected: a "Not saved — keep this page open" warning with Retry on the access screen. Disproof: the screen shows "Your request is with the admins" with no warning, and storage has no request row. Also run it on an iPhone: close the tab and the request is lost with no prompt (iOS never fires the leave prompt — `boot.ts:78-86`).
2. **A failed save is hidden by signing out.** Setup: admin, storage refusing writes, then a schedule edit, so the warning shows. Action: Sign out → the sign-in screen → sign in as a guest, then as a pending person. Expected: someone is told before or after the sign-out (sign-out asks, or the sign-in screen shows the warning). Disproof: the warning vanishes and the unsaved work sits in the saver while nobody is told. Then sign the admin back in: the warning reappears for him with no word about which change. Repeat with a member's own input.
3. **A save left over from the last visit fails with nobody told.** Setup: reload with a half-finished save group in browser storage; the saver starts in the failed state (`storage/boot.ts` around line 50). Action: land on the sign-in screen, then sign in as a guest or pending person. Expected: a warning on these screens. Disproof: nothing is shown until an admin or member signs in.
4. **The posting pass runs and saves during a guest or pending session.** Setup: a posting dated tomorrow, a guest session open (tab left open over midnight, or the date set forward). Action: the guest taps a week or swipes a day. Expected: the pass's save failing is told to someone. Disproof: a `lw.postoutRun` group is saved, or fails, with no screen able to say so. Also check the change history's name on any lines it writes: the guest is named "Guest" (`store.ts:860`).
5. **A member's own posting date arrives mid-edit.** Setup: a member with the input window open and changed fields, or mid-way through his Quals row; his posting date passes. Action: any tap. Expected: his edit is saved or he is told it was lost, and the pass's save failure is visible. Disproof: the screen jumps to "Your access is suspended" (`App.tsx:38-43`), the typed edit is gone silently, and the suspended screen has no warning.
6. **The member presses Publish AL# on Edit Schedule.** Reach: the localhost bridge only — `raptorRole('member')`, then `setPage('editsched')`, on a published day whose working copy changed and is fully signed off. Action: press "Publish AL1" in the Amendments panel, by mouse and by keyboard (Tab, Enter). Expected: not drawn for a member, or refused with words. Disproof: a live button, no message, storage unchanged, the Undo list unchanged. Note this as defence in depth, because no production route was found.
7. **Every other control on Edit Schedule, as a member (same bridge setup).** Tab through the whole page and press everything:
   - week chips, the jump-to-date calendar, CSV, PDF, Highlight, Insights, search;
   - the Amendments panel and its issued list;
   - the legend;
   - every day head: version dropdown, plan selector, Templates, the "N new / changes" button;
   - the crew panel: fold arrows, crew-day step, crew pucks, and the CREW rail.

   Expected: any text box that takes a caret is a finding. Any press that changes storage is a finding. Any press that does nothing and says nothing where a scheduler's would act is a finding. Typed text left on screen that was never saved is a finding (`textedit.ts:152` returns before saving or putting the box back).
8. **The Scheduler Board reached as a member.** Reach: bridge, member, then open the board by setting the board's day directly. Action: press everything on the board and its More menu, type in every box, drag a puck, use the sign-off strip. Expected: read-only throughout, and its warning band still works. Disproof: any write, or text left typed but unsaved.
9. **A new input for another man is still live after the switch to member view.** Setup: admin on Inputs opens a NEW input for another man (with the scheduler-only "Goes to" set). Action: tap his name badge while the window is up (or switch from the phone menu), then press Add. Expected: the window closes or turns read-only. Disproof: Add is still live (`InputWindow.tsx:753` — a new input is never read-only), and pressing it gives a refusal whose words do not say why, or something gets saved.
10. **An existing input of another man, same switch.** Expected: the window turns read-only at once (Close, no Save). Also check the scheduler-only marks (LATE dropped, cancel reason) are no longer pressable.
11. **Leave War admin sheets left open across the switch.** Sheets: open bidding dates, settings, grades, a person's window, approvals. Action: switch to member view (badge if it can be reached, else the menu), then press Save or Approve. Expected: the sheet closes, or the refusal is said in words. Disproof: silent, or a "try again" wording.
12. **The Tracker's flex settings left open across the switch.** Action: switch to member view, change a figure, save. Expected: refused, with words. Disproof: the Tracker's "saved" corner says saved, and storage is unchanged.
13. **The admin's own steps carried into member view.** Setup: admin changes a duty template (or a schedule cell), then switches to member view. Action: Undo, and Redo after an undo. Expected: "Switch back to the admin view to undo that." and no page jump. This is checked at `timeline.ts:913`, before the screen moves at `920`. Disproof: the page jumps to Admin or Edit Schedule, or storage changes.
14. **Body-level popups across the switch and across sign-out.** Popups: the stores box with its pen, the add-wave menu, the plans selector, the day-template menu. Action: open each as admin, then tap the badge (or sign out). Expected: each is removed (`view.ts:626-630` removes `.stmenu, .wavemenu` on a page change). Disproof: a popup survives with live buttons. Check which class the plan and day-template menus actually use.
15. **Two tabs, with a suspension in one.** Tab A: admin suspends or archives member M. Tab B: M signed in, never told, keeps filing inputs and editing his Quals row. Accounts are read once, and `sessionNow` reads what the tab already holds (`accounts.ts:515-525`). Observe: are M's writes saved, and does his Quals row write bring the person back to unarchived in storage? This is new-data harm. File it for the database step if the server is the intended guard.
16. **Two tabs, pending person.** He files a request in tab A and again in tab B. Expected: one request. Disproof: two requests for one sign-in name (`accounts.ts:431` checks only what that tab holds).
17. **`?fresh=1` on the deployed host.** Action: a member files an input or a pending person asks for access, then reloads. Expected: the parameter is ignored outside dev and test, or the screen says nothing is kept. Disproof: writes are accepted, the status reads saved, and all is gone on reload. Under the shared-store setting this also makes the first admin in memory.
18. **Browser storage that cannot be touched** (locked-down browser or private mode). Same expectation and disproof as 17, for every role.
19. **A role refusal surfaces as "Couldn't save that — try again".** Probe every member action that reaches a refused schedule command: the schedule backstop, a sign-off select left on screen from stale markup. Expected: words that say whose job it is. Disproof: "try again" (`sched-commit.ts:663`).
20. **Admin typing in a schedule box, then tapping the badge.** Expected: the text is saved as the admin's own change before the switch (the box lets go of the caret before the click) and his name is on the change history line. Disproof: lost, or saved under the member view.
21. **A drag in progress when the session changes** (posting pass, or sign-out from the phone menu mid-drag). Expected: no drop lands and no ghost puck is left behind. Low.
22. **A guest's week navigation and the OIL pass.** Measure storage before and after a guest's week tap and day swipe across 3 weeks. Any saved `lw.sync` group under a guest is a save nobody can be told about. Caveat: this may happen only on the authored demo weeks, which are not stored data. If the shared-store setting writes nothing, it falls under the stored-demo-data exclusion (D56).
23. **The guest switch turned off, or the request answered, while a guest is viewing.** Expected: no write is possible either way. Note that `sessionNow` ignores guest and pending sessions, so he stays a guest until he signs out. Low, and not a write.

### Checked, no route found (negatives)
- **No URL hash routes and no other query route.** No `hashchange` or `location.hash` use anywhere; the only query parameter is `?fresh` (item 17).
- **No production route puts a member on Edit Schedule.**
  - Nav tab: `hidden={!admin}` at `Shell.tsx:377`; phone menu at `Drawer.tsx:26`.
  - Undo landing: only when `canEditSched()` (`undo-wire.ts:158, 245`).
  - Page reopen after Retry: only the Leave War or the Tracker (`pagedownload.ts:75`).
  - Opening the board: `interactions.ts:910/924`.
  - The admin's switch leaves Edit Schedule and Admin (`store.ts:506`), and leaving Edit Schedule closes the board (`view.ts` setPage, `closedBoard`).
- **The Admin page refuses a member** with a message (`AdminPage.tsx`, "Admin tools are for schedulers").
- **These windows hide or refuse for a non-admin:** drafts, day, duty and wave templates (`DraftsModal.tsx:45`, `DayTplModal.tsx:43`, `DutyTplModal.tsx:43`, `WaveTplModal.tsx:53`), and Inputs and SANS settings (`InputsSettings.tsx:38`, `SansSettings.tsx:37`).
- **Planning-calendar writers check the role first** (`plan.ts:61, 99, 111`).
- **Logic page writes check for an admin** (`LogicPage.tsx:332, 340, 360`).
- **The developer bridge exists only on this PC.** Only localhost, 127.0.0.1 and ::1 (`probe-bridge.ts:56-60`), checked again at `:66` and at `main.tsx:58`. To confirm on a preview link: `window.setPage` and `window.raptorRole` are undefined there.
- **A guest has no Undo and no shortcuts.** GuestApp mounts none of Shell's document-wide listeners. The main app has no global Ctrl+Z (`textedit.ts:406` handles Enter/Escape only). The Tracker's Ctrl+Z is bound only while its tab is up (`tracker/app/core.js:3181-3195`).
- **Sign-in and sign-out start the next person clean.** They clear Undo, every window, the board and the armed seat (`store.ts:412-479`).
- **A crew-panel tap that hands over an input** (`interactions.ts:1375`) needs an armed seat, and the switch clears it (`store.ts:507`).

### Plain-user rounds (D1557)
- **Member.** Sign in → View-only Sched → swipe and arrow across 2 weeks. Open a day's ⓘ panel, close it by ✕, by Escape and by tapping outside. Switch a published day to its working draft and back. Inputs: file his own leave, edit it, delete it, Undo, Redo. Quals: his own row — tick a qual, change a CAT; check the Management column and his callsign are refused. Open the bell and the changes window; "Mark all as seen". Leave War: bid on his own row, then try another man's row. Tracker: one edit, then Undo. Sign out. Then look everywhere the result should show: the Inputs page, View-only Sched, the bell, his person window, another week. Throughout, storage should change only by his own rows, and no failed-save warning should appear unless saving was made to fail.
- **Guest.** With the admin's guest switch on: sign in on an unknown name → Request access (blank fields first, then over 14 letters, then valid) → the waiting screen → View the schedule. Tap every week chip and swipe days. Try to open ⓘ, the working-draft picker, a puck's long-press, any text. Sign out → sign in again on the same name (straight to the guest view). Then, as admin: Admin → Users shows exactly one request. Storage before and after the guest part should differ only by that one request (plus any system pass, which goes back to item 4 or 22). Repeat the round with storage refusing writes (item 1).
