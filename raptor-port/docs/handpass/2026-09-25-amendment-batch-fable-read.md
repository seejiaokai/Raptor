### Findings, by consequence

**1. The load leaves a two-day request "taken off" while its row is back on the programme — a filing lie that the next AL freezes. Already on `main`; the batch fixes it for one-day requests and names the two-day case, but names it wrongly.**
Scenario: a request covering Mon–Tue is accepted onto Monday (its one row lands there). Monday and Tuesday are both published. The scheduler taps ✕ on the row (the row goes, the request reads "taken off"). He then opens Monday's Original and taps "Load onto working copy". The load puts the row back (it is in the version), but the request stays "taken off": the general reconcile in `slots.ts reconcileDayFiling` deliberately skips a removed request, and `publish.ts filingRestorePlan` sends every request that also covers another loaded day to `left` before it looks at whether the row now stands on this very day. Result: Monday shows the row on the programme AND "1 pending — on the programme → taken off"; the toast says "1 request also covers another day — left as filed", which is not what happened (the row came back). D98's promise ("the day reads exactly as that version, nothing pending") is not met. If he publishes AL1 now, the record freezes "taken off" beside a standing row. The request's own ✕ then refuses (it already reads removed) and a fresh Accept refuses (a row with its key exists), so the pair is stuck until the row is deleted by hand.
Fix: in `raptor-port/src/engine/publish.ts`, `filingRestorePlan` — compute whether the row stands on THIS day (`j===di` in the `landed` scan, a separate flag `here`); when `want==='g' && here`, `put` it BEFORE the "covers another loaded day → left" test (the version's own row on the loaded day is the fact; a filing that says otherwise beside it is exactly the dangling state P2-REV2-05 forbids in the other direction). In `raptor-port/src/engine/drafts.ts`, `loadVersionToWorkingCopy` — such a request is already in `multi`, so it lands in `LOADMOVED` by itself; in `raptor-port/src/ui/interactions.ts` (the Load handler's message, ~line 1012) word that branch both ways ("came off … / came back onto the programme with its row — Tue reads that too"). Add a test beside `amendbatch.test.tsx` item 6: two-day request accepted on Monday, both days published, ✕, load ORIG on Monday → `acc==='g'`, `dayDelta(MON)` empty, `LOADMOVED` names Tue. `dayDiscardCount` shares the plan, so the confirm agrees automatically.

**2. The "Discard N edits" confirm can count a filing the load will not touch. NEW.**

Fix: `publish.ts filingRestorePlan` — skip `inputProtected(inp)` inside the loop (one place, both callers agree); drop the guard from `drafts.ts`.
