## Findings

### 1. HIGH · OLDER — a published, woken request can later disappear or change without pending/signature invalidation

Setup:

1. Take a request off (`acc:'r'`) and publish it.
2. Retype it on the same day; this correctly wakes it to `acc:''` and creates one pending change.
3. Sign and publish that change, making the live request the new issued baseline.
4. Delete it, re-date it off the day, shorten a multi-day span off the day, or reassign/edit its live input values.

Expected: the issued face contains a live request while the working copy does not, or contains different request data; the day must show pending, the four signatures must fall, and the issued face must remain unchanged.

Actual:

- `publish.ts:374-376` normalizes both “issued key present with `''`” and “current key absent” to `''`, then returns true through `a===now`.
- Reassignment and other value-only edits retain the same iid and `acc:''`; the filing fingerprint therefore does not change at all.
- `dayDelta` remains empty, so every count/list and the publish gate read zero; `currentBind.pd` also remains empty, so signatures hold.
- Published rendering still reads the live `INPUTS` collection. Once the input is deleted or moved, the frozen filing map cannot reconstruct it, so the supposedly frozen face changes too.

This is not old-data compatibility: the sequence reproduces with newly created data. The direct D176 `r → missing` case is correct; the failure begins after the explicitly tested wake is itself published.

Fix:

1. Make filing equality membership-aware before comparing normalized values. Permit only the two decided missing/dormant equivalences:

   - issued absent ↔ current present `r` (D174);
   - issued present `r` ↔ current absent (D176).

   Issued present `''` ↔ current absent must differ.
2. Represent/freeze the relevant input values for an issued day, not only iid→acc—either an immutable per-snapshot input projection or retained versioned input records—and make all issued-face input readers use it.
3. Ensure value-only changes to a live issued request—person, type, timing, remarks where displayed, dates—enter the canonical delta/signature binding.
4. Preserve the D174/D176 exceptions when adding that membership/value comparison.

Tests:

- Extend `reqonerow.test.tsx`: `r` published → retype/wake → publish AL → delete; expect one pending item, `dayHasChanges=true`, and `daySigned=false`.
- Repeat with re-date, multi-day shortening, and reassignment.
- Assert the official/published face remains byte-equivalent to the newly issued face after each working-copy mutation.
- Pin undo/redo, week-away-and-back, and Load: undo restores zero/signed; redo restores pending/unsigned; Load cannot claim zero when the deleted request cannot be restored.
- Pin Unpublish: reverting from the fresh-input AL to the preceding dormant version legitimately returns to zero, while clearing signatures as Unpublish already does.

### 2. LOW · NEW — the official-warning divergence reader was not taught D176

For the exact D176 case, `dayDelta` now says `r → missing` is equal, but `weekctx.ts:249-273` still treats any membership mismatch as divergence. Consequently `validate.ts:1384-1389` performs the full official validation pass on every validation instead of aliasing working and official results. The cross-week `windowDiverges` path has the same disagreement.

This did not reveal a wrong displayed result for the exact dormant case, but it is a permanent extra validation pass and contradicts the stated one-comparison rule.

Fix:

- Share one pure filing-equivalence helper between `publish.ts` and `weekctx.ts`.
- Preserve membership sensitivity for present-empty versus absent, while normalizing only D174 absent↔`r` and D176 `r`↔absent.
- Add direct `filingDivergesAt` and cross-week pins for those four membership combinations.
