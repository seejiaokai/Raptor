## 2. THE DOOR THAT WAS NOT FOUND — closed

The 21 Sep session filed a blocker: a request's own edit button (`data-inpedit`) "is NOT in the DOM"
on the board, with the edit-mode hook reading false. Every remaining scenario that edits a request
was stuck behind it.

**The button was never missing.** The board's PERSONAL INPUTS panel folds to a one-line summary by
default — *"3 inputs · 3 on programme · show ⌄"* — and folded it renders **no rows at all**, so the
button is absent rather than hidden. The header itself is the toggle. Pressing it: **0 → 3** edit
buttons.

Two traps written into `scripts/handpass/lib.mjs` (`openInputs`) so nobody pays for them again:

- the toggle attribute rides the header in **both** states, so its presence says nothing about which
  way the panel is folded — a naive "is it shut?" check closes an open one. Read the ROWS.
- the fold is `!readOnly`, which is why the rows DO appear once the OIL mode is on — and why the edit
  button there is correctly replaced by the OIL cell.

## 5. WHAT THE WALK FOUND — three defects, all fixed, all re-walked

Every one was invisible to the gates, to both code reads, and to the existing tests.

### 5.1 Undo's boundary was wired to a button nobody can press

Fix 5 says the press that would reach past the mark leaves the mode instead of changing the day. It
does — from `#undoBtn`, the **page's** Undo, which is the only caller of the guard. That button is
covered by the board's own sticky top bar whenever the board is open (measured with
`elementFromPoint`: it returns the top bar, not the button), and **the board is the only place the
mode exists**. The board's own Undo went straight to the real undo.

Driven as a person drives it, the third press walked back a ground-row change underneath a screen
that says the schedule cannot change — silently, mode still open.

**Why every test passed.** `oilundo.test.tsx`'s helper is
`pressUndo = () => (oilUndoBoundary() ? … : globalUndo())` — it reimplements the handler, so the file
would pass identically if no control anywhere called the guard.

Fixed: both buttons carry the same two steps. `oilundo-button.test.tsx` presses the real button on a
rendered app; red first. **Re-walked:** press 1 and 2 take back the OIL decisions ("Undid: a change
to the schedule"), press 3 says *"Left OIL Earn — the next undo would change the day itself"* and the
schedule is untouched, press 4 — outside — undoes it normally.

**Also noticed, not fixed:** presses 1 and 2 say *"Undid: a change to the schedule"* when what they
undid was an OIL decision. Filed, not on this branch.

### 5.2 A claim row said the opposite of the puck beside it

Four rows on the everything-Saturday carried both at once: the name cell *"Nothing on this row can
earn OIL, so there is nothing to switch off"* and, on the same line, *"Talisman earns half a day"*.

`oilCapableItems` is derived from the SCHEDULE walk, and a request's money never goes through it — the
requester is paid from his own answer and D18's extras are each decided on their own puck. So a live
claim is absent from that set for a reason that has nothing to do with being unable to earn.

Fixed: a live claim now says *"A request is answered for each person on it — tap a puck on this row,
not the row itself"*. Cancelled, ⓘ, withdrawn and unreadable-week claims **keep** the old wording,
because there it is true — asserted, so a fix that merely deleted the sentence would not pass.
`oilclaimrow.test.tsx` asserts the invariant over every row the board draws. **Re-walked:
contradicting rows 4 → 0.**

### 5.3 D18's second man was paid and told he earned nothing

## 10. What this walk cost the method

Per §11 of the order — every defect found is a method failure before it is a bug, and pays a line.

1. **A test that reimplements a handler's steps proves the rule, never the wiring.** §5.1. A guard
   with fewer call sites than triggering controls is a reachability bug. New anti-pattern:
   **the handler re-enacted** — a test that calls a guard and then the action, instead of pressing
   the control that should call both.
2. **Absence of a DOM node is not evidence a feature is unbuilt.** §2. Read what IS rendered there
   first — a folded panel, an empty state, a "show N more" summary all present as a missing node.
3. **Two bodies answering one question is the defect, not the symptom.** §5.3. When money moves to a
   new body, every reader of the old one is a roll-call row.
4. **A list that draws the same check on two surfaces is two surfaces.** §5.4. The roll-call has to
   cover the WARNING LIST as a drawer, not only the puck.
5. **A measurement against a faded element reads as absence.** Items 10 and 17 were reported as
   defects for a day because the message element fades instead of being removed. Read state, not
   liveness.
6. **The roll-call must cover where a thing can be PUT, not only where the fixture has it.** §11 — every ALL AVAIL row this walk examined was one the demo seed already had, which happened to be one of the two places it is honoured. The owner put one somewhere new within minutes.
7. **A control that proves nothing when the subject already has the thing.** §4's trap line — job 8
   with a man already earning. The fixture has to start from the negative.

### 11a. D27 reshapes it, and what it costs — the agent's answer to his question

**His intent (D27, 22 Sep 26):** ALL AVAIL / ALL are a SCHEDULING feature. Dropped anywhere in the
schedule they work out who would be available to attend and SHOW THE COUNT — by default, with OIL
Earn switched OFF. He also leans against either puck EARNING on a duty desk, and asked: *"Does it
hurt that all avail and All pucks works on anywhere in the schedule? … Would it cause a lot more
bugs?"*

**The answer is the split between DISPLAY and EARNING, and it is not symmetrical.**

- **Display is a READ.** Nothing is owed, nothing frozen, no amendment. Allowing it on every seat is
  cheap and low-risk: a wrong number is visible and harmless.
- **Earning is MONEY, and every earning seat is a money surface FOREVER.** "Available" is a live
  answer; money must come from the issued document. The freeze already exists — the evidence block
  stores the participants at publication, so an issued ALL AVAIL event's people cannot change under
  the reader — but it is exercised only by the two paths that honour the puck today. Each new earning
  seat has to be walked through that freeze, and its failure mode is SILENT: a man paid or not paid,
  with nothing on screen and no error.
- **Flexibility that is allowed but unused still has to be kept correct**, on every future change
  near those seats. That is the real price of "just in case", and it is a standing price, not a
  one-off.

**RECOMMENDED SHAPE — his call, not yet ruled:**

1. **Placeable and DISPLAYING everywhere** — D27's half, and the useful one.
2. **EARNING from a short explicit list**, today only the Common Programme and the Ground Programme,
   the two that already work. Duty desks off, per his lean.
3. **That list lives in ONE place**, so adding a seat later is a one-line change plus its own check
   rather than a redesign — the flexibility banked at no standing cost.
4. **Wherever it can be PUT but cannot EARN, the app says so** ("shows who's available · this event
   earns no OIL"). This half the agent fixes whichever way he rules; it is what stops the silent bug
   in both directions.

**Size, honestly:** D27 is not small. The counter is currently part of the OIL mode's own decoration,
so making it an ordinary property of the puck means drawing it on all six seat types OUTSIDE the
mode — the same roll-call again, but for a READ, so no money risk inside it.
