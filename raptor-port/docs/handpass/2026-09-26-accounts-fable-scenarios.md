## 1. Roll-call gaps

Readers or doors of "who is signed in" that §Roll-call (39 rows) and the Doors list do not name, or name with a promise the code does not keep.

1. **The "change sign-in name" door does not answer a waiting request.** `raptor-port/src/state/accounts.ts:220` (`updateAccount`, the `name` patch) checks `nameProblem` against accounts only. `addAccount` (line 209) and `approveRequest` (line 238) clear a request under that name; the rename does not. After an admin renames an account to a name that is waiting, the request stays listed, `signIn` (line 152) resolves the account first so the person is in, and approving the stale request is refused with "already has an account". The plan §7 states the rule only for "adding an account". New data, going forward, so in scope.
2. **The member's only Undo door is the Leave War's pair.** `raptor-port/src/ui/Shell.tsx:333` mounts the Undo/Redo pair only on Edit Schedule, which a member never sees. A member's undo of his own input or bid is reachable only through `raptor-port/src/leavewar/ui/Chrome.tsx:108-123`. Roll-call 20 and the "Member walks: undo of own change" order name no surface; the walk's `d-undo-fresh` drove the admin's pair only.
3. **The admin's bug-report list prints the name as filed, not the live callsign.** `raptor-port/src/ui/HelpPage.tsx:39` renders `r.who`; the plan §8 and roll-call 22 promise "displays the live callsign" via `pid`. Only "Your reports" (line 74) is keyed by `pid`. A member renaming his own callsign (D149) makes the admin's list disagree with every other surface.
4. **A door drawn for a member only to refuse him.** `raptor-port/src/ui/html.ts:1104` draws "Create the YYYY period" inside the day's warning box on View-only Sched (`!PV`), and `raptor-port/src/ui/interactions.ts:1156` refuses a non-scheduler on tap. It reads `canEditSched()` (so `perms`) but is not in roll-call 33/34/35, and it is a Raptor surface that reaches a Leave War admin-only writer (`createWar`).
5. **The Leave War `viewer` is written by the sync on notify, not by `resetSession`.** `raptor-port/src/leavewar/sync.ts:1427` and `:1436` call `setViewer(viewerId())`; `raptor-port/src/state/store.ts:289-356` never does. The plan §4.4 says role and viewer are "written ONLY by resetSession". Every production caller of `resetSession` (`Login.tsx:27`, `logout.ts:13`) calls `notify()` next, so nothing renders in the gap, but the roll-call's "proved by" for row 11 rests on a seam that is not where the plan says.
6. **The loaded week is inherited.** `resetSession` resets pages, selection, pops and the undo list but not `CURWEEK` (`engine/waves.ts`) or the per-week stash. The next person, a guest included, lands on the week the last person left loaded. Not in the roll-call or §3's list; not a permission leak, but it is "what the next person inherits".
7. **Two refusal wordings can mislead.** `raptor-port/src/state/quals-write.ts:87` maps any `invalid` commit (a hard-invariant rollback or a reducer throw, whatever the cause) to "You can only edit your own row", so an admin whose own edit rolls back for another reason is told the wrong thing. `raptor-port/src/state/accounts.ts:175` surfaces `r.message` raw, so an ownership breach would print a record path such as `an admin's record (settings/accounts)`. These matter for the observation column below.
8. **The last-admin guard is unreachable from the app.** `raptor-port/src/state/accounts.ts:225` counts the acting admin himself (on, admin, person exists) and line 218 forbids him touching his own account, so no click path can leave zero admins. The plan's order "demote / switch off the last admin (refused)" cannot be driven through the UI; the guard is unit-tested only. Not a defect, but the walk should not claim it.
9. **A renamed seed keeps its code-only password.** `raptor-port/src/state/accounts.ts:154` keys `SEED_PASS` by account id, so after the admin renames `ad` to `saber@mail` the new name still demands `a`, and the edit form says nothing. Demo-data edge (D56 covers the seeds themselves), noted only because the rename door exists.

## 3. Explicit negatives

- **App tree and the five session states:** `App.tsx` routes `null → Login`, `pending/off → AccessScreen`, `guest → GuestApp`, else the Shell; `sessionFor` and `signIn` cover every row of the plan §2 table; no gap.
- **The sign-in card:** unchanged markup; wrong seed password refused; empty fields refused; no gap.
- **Every window closes at a session change:** `POPS_RESET` lists every `export let` in `pops.ts`, `AVAILWIN`, `SECDEFOFFER` and the toast ride `VIEW_RESET 'session'`, `resetSession` calls it before `setMe`; the Shell and every modal unmount through Login between two sign-ins, so React-local state cannot carry; no gap beyond the loaded week (roll-call gap 6).
- **Undo:** `endUndoSession` clears entries and both seq maps; the board's, the top bar's and the Leave War's pairs all read the one timeline; `mayReverse` needs a person; the legacy `HIST` stack has no UI door; no gap beyond the door location (gap 2).
- **The command gate:** every registered type is in `COMMAND_OPS`; `cmdAuthorize` refuses guest/pending/off except `access.request`; the ownership invariant is installed in `wireStore`; the sync passes (`runOilPass`, `runPoArchive`, `reprojectRoster`) run as projections with the system actor; `loadWeek` is a raw path; no gap found by reading (S2/S5 walk the unwalked paths).
- **The pending person's request:** the principal comes from `SESSION.name`, normalised at sign-in on both sides of the owner check; only `accessreqs` may change; twice refused; no gap.
- **Accounts UI guards:** own account disabled with "you"; the archived tag; "switched off" tag; the pickers exclude special, archived and linked people; relinking to an archived person refused; no gap beyond the rename door (gap 1) and the unreachable last-admin guard (gap 8).
- **The guest render:** `viewDayHTML` guest branch, no working-copy picker, no ⓘ, plain day head, no warning box, medical hidden by `hideMed` (label and remark cell; types by `isDownchit`), no `routeClick`, no keyboard router, no Shell listeners; DocViewer, Help, Tracker, Leave War not mounted; `fileReport` refuses non-members; no gap.
- **Medical for members:** `hideMed` false for every admin and member; the Inputs table's 📎 ungated; the Medical view's card tap ungated for viewing with Edit/Upchit gated in the viewer footer by `isMe`; matches D211; no gap.
- **"Who" records:** edit log rows carry `who` and `pid`; unpublish `by` is the actor's person; bug reports carry `pid`; the Tracker stamps `whoami`; the war's `approverName` reads the viewer; no gap beyond the admin list's display (gap 3).
- **Inputs page:** admin's Person default and filter default; member's `#inPersonFixed`; row ✎ ✕ OIL by `canEditSched() || isMe`; `inputedit` files for the signed-in person; `caldrag` refuses others; no gap.
- **Top bar and drawer:** no `#viewAs`, no `#drawerViewAs`, no `#drawerRole`; badge inert; Admin and Edit tabs hidden for members; `#admDeny` at the page; no gap.
- **Leave War role:** written by `resetSession`; the Chrome hides "New war", the stage button, the sync-clash strip, and disables the bid window for members; no gap.
- **Logout paths:** the top bar, the drawer, all three access screens and the guest bar go through `logOut` → `trackerMayLogOut` → `resetSession(null)`; no gap.
- **Persistence:** the three keys are in `SETTINGS_KEYS`, `accountsLoad` is in the loader list and in `initStore` after `hydrate`; the loader never writes; no gap.
- **The walk script itself:** its sign-in/sign-out helpers cover every logout door; it never has a member file an input, bid, undo, or drive the guest's week chips, and never renames a callsign, relinks a puck, posts someone out, or turns the guest switch back off, which is what S2, S5, S6, S8, S9 and S10 add.
