## The rule, and what the code now does

- `filingSame(was,id,now,present)`: was `'r'` and the request no longer covers the day (`present` false) → same. Every
  other pair is as before: absent→`''` same, absent→`'r'` same (D174), `''`→`'r'` differs, `'g'`/`'u'`→anything else
  differs.
- `filingDelta` passes `present = hasOwnProperty(now,id)`, where `now` is `dayFilingFingerprint` — every live input
  covering the date. So `present` false means exactly "deleted, or no longer covering this date". Correct.
- `filingKey` now leaves a live `'r'` out of the signature when the issued record holds `'r'` (D176) or never held it
  (D174). Before the change the key carried `k=r` when the record held `'r'`, so a deletion changed the key and the
  four fell on a day nothing changed. After it the key is the same before and after the deletion. A woken request
  (`'r'`→`''`) leaves the key alone (`''` is never keyed) and falls through `pd` instead — checked, and pinned by the
  third D176 test.
- `filingRestorePlan` calls `filingSame` with three arguments over live inputs covering the date, so `present` is
  always true there: the load's put-back is unchanged by this build. Checked.

## Findings (ranked)

### F1 — OLDER, medium, ALREADY FILED: an input the record holds `''` (waiting, or a leave), since deleted or re-dated off the day, reads 0 and keeps the four

`filingSame`: was `''` (held), now gone → `now` reads `''` → `a===now` → same. So a leave that WAS under Unavailable when
the day was published and is since deleted vanishes from the published face (the Unavailable block reads live INPUTS on
every face — `html.ts` line 1828) with 0 pending and the four standing; a waiting Meeting that flagged on the issued
face likewise. This is the mirror of D177 (an input going OUT), and it contradicts the D174 half that says a request the
record DID hold and now taken off counts one: `''`→`'r'` reads 1, `''`→gone reads 0.

**Not caused or touched by this change** — the same on `main` — and **already in D177's sweep** as A1 in
`docs/superpowers/specs/2026-09-25-published-face-live-inputs.md` ("a leave (or any never-actioned input) that
EXISTED at publish, since deleted or re-dated off the day … D177's mirror"). Nothing to do on this branch. **A note for
that build:** `filingSame`'s `a===now` clause must then be split — held `''` matches a live `''` only while `present`;
held `''` against gone is a difference — and `filingKey` needs no change for it (`''` is never keyed; `pd` carries it).
The test: a leave (OL) for Hunter on Monday, publish, sign the four, `removeInput` → expect `dayShownPendCount(MON)` 1,
`daySigned(MON)` false; then the re-date variant.

### F2 — OLDER, low: the pending list cannot name a deleted request that had no row

`pendlist.ts requestWords`: the input is gone, so the line is named from a row; a request filed under Unavailable
(`'u'`) has no row on either day, so `requestName(null, undefined)` gives **"A request · under Unavailable → deleted"**
— whose, and what, are not said (D99: the list exists so the scheduler never has to hunt). The paired case
(`'g'`→deleted) is fine — the D114 fix names it from the issued row. Reachable today: a request filed "→ Unavail" on a
published day, then deleted on the Inputs page. **Fix:** the fingerprint is acc-only, so the name must come from
elsewhere — the cheapest honest source is the edit log's own "Input removed — Bane, Meeting, Jul 13" row
(`removeInput` writes it), matched by the input's id if `logAction` is given the iid to carry (one field on the log
row), else by person + type + date from the frozen day's `dt`. **Test:** `acceptInput(MON, inp, 'u')`, publish,
`removeInput(inp)`, `pendListHTML(MON)` → `.pl-where` contains Bane's callsign and "Meeting".

### F3 — OLDER, low, NOT reproduced (read only): a plan switch can put a row back beside a dormant `'r'`, and a later delete then leaves that row behind

`draftSelect` → `reconcileDayFiling`, which leaves `'r'` untouched (it is a filing decision, not a landing). A plan
parked WITH the request's row, the request ✕'d meanwhile (`'r'`), then the plan switched to: the row is back on the
day while the request reads "taken off" (its Accept button then does nothing — `acceptInput` sees the row and refuses).
Delete it on the Inputs page: `dropInputRow` → `unacceptInput` refuses `'r'` → the row stays with a dead `src` — the
exact shape `removeInput`'s own comment says it exists to prevent. Outside this brief (the plan switch is not a way a
request stops covering a day, and `filingRestorePlan`'s comment already names `'r'`-beside-a-standing-row as the state
P2-REV2-05 forbids); reported so the parent can decide whether it goes to the backlog. **Fix if taken:**
`reconcileDayFiling` re-files `'r'` to `'g'` when its own row stands on a loaded day (the `landed` branch already
does this for a falsy acc; extend it to `'r'`), or `dropInputRow` removes any row whose `src` is the deleted id whatever
the acc. **Test:** `acceptInput(MON, inp, 'g')`, `draftDup(MON)`, `unacceptInput(MON, inp)`, `draftSelect(MON, planA)`
→ expect no row with `src === inpId(inp)` OR `inp.acc === 'g'`; then `removeInput(inp)` → expect no row.

## Explicit negatives

- I checked every caller of `filingSame`, `filingDelta` and `filingKey` in `src/` (grep, tests excluded) and found
  nothing beyond the roll-call above.
- I checked that `present` can only be false when the input is gone or no longer covers the date, and that no
  other state (`'g'` on another day, `'u'`, protected) reaches the new clause.
- I checked the woken case against the signature: the `fil` axis is unchanged (`''` is never keyed) and the `pd` axis
  carries the `'r'`→`''` entry, so the four fall — pinned.
- I checked that neither door under D176 leaves a raw pending mark (`markInputDays` is not called on a dormant
  request's delete or re-date), so an Unpublish afterwards cannot surface an inert "1 pending".
- I checked the D114 pairing for a `'g'`→deleted request: paired with the issued row's delete, one item, named — unaffected.
- I checked the load's put-back and the discard count: unchanged by this build (`present` defaults true there).
- I checked the official-pass gate (`filingDiffers`): membership-aware and separate; a deletion forces the pass, and
  the pass reads the frozen `'r'` — no visible effect, and the same before this change.
- I checked `engine-rules.md` §Publishing's D176 sentence and the `[REQ-DECLINED-DELETED]` item against the code: they
  match.
- Excluded by the brief, stated so nobody re-finds it: a signature given BEFORE this build on a day whose record held
  `'r'` carries `k=r` in its stored `fil`; today's key leaves it out, so that one signature falls once and must be given
  again. Stored data only; the code is right going forward.
