# Astra independent review — D114

## Verdict

I found two additional issues:

1. **Moderate — the pending list still ignores D119’s newest-first order.**
2. **High — loading a version or parked plan can give one request two live programme rows.**

Neither was introduced by `a95afcbe`. The D114 pairing added by that commit is correct in the ordinary accept/remove paths. I deliberately omitted the two host-owned §9.5 findings.

I read commit `a95afcbe`, the named rulings and contracts, the host’s §9 roll-call, the relevant production callers and tests, and compared against `main` and `301a11fc`. I did not read another reviewer’s report, edit files, run tests, or run a build.

## Ranked scenarios

1. **Pending-list order:** make an older flying change, then a newer ground change; open “N pending ▾”. Expected: ground change first. Disproof: flying remains first because section rank wins. **Finding 1.**
2. **Older-version load after relocation:** move a two-day request’s landing from Monday to Tuesday, then load Monday’s issued version containing its former row. Expected: refuse without changing either day. Disproof: the request appears on both days. **Finding 2.**
3. **Parked-plan equivalent:** park a Monday plan containing the row, move the request to Tuesday in the live plan, then switch back. Expected: refuse the conflicting switch. Disproof: both rows become live. **Finding 2, same root.**
4. **Ordinary multi-day removal:** remove the request’s only row. Expected: one paired item on its row day and one filing-only item on each other published covered day. **Correct.**
5. **Row already on another day:** a covered day with no row of its own retains a standalone filing item. **Correct.**
6. **Undo then “→ Unavail”:** the final `g → u` filing pairs with the removed row and reads as one request transition. **Correct.**
7. **Plain row delete:** deleting a linked ground row routes through `unacceptInput`; a stale `src` with no request remains an ordinary one-row removal and is not falsely paired. **Correct.**
8. **Inputs-page edit:** an accepted request is unlinked and relinked through the shared engine path; if it remains accepted, only actual row-field differences remain. **Correct.** The host-owned deleted-input wording issue is omitted.
9. **Undo/Redo:** state restoration recalculates the items; no D114-specific cache or derived count is persisted. **Correct.**
10. **AL after AL:** removing the request and later accepting it again are each compared with the current issued version and each freeze one item. **Correct.**
11. **Two requests for one man:** stable `iid`/`src` identity prevents the pair from crossing between requests. **Correct.**
12. **All count surfaces:** apart from the host-owned discard/load issue, the day head, board, day panel, sign-off line, Amendments panel, pending-list heading, publish toast, plan-switch message and issued-AL count share `dayPendingItems`. **Correct.**
13. **Issued records:** `units` and `ukinds` are frozen at issue, copied into retired records, accepted by schema validation and restored whole by undo/persistence. **Correct.**
14. **Empty-list invariant:** pairing attaches the filing entry to an existing item; it does not discard the last difference, so an ordinary valid state cannot have an empty item list with a non-empty `dayDelta`. **Correct.**
15. **Old stored AL without `ukinds`:** the diff fallback can show the older split, but D56 excludes this demo-data-only case. **Not a finding.**

## Finding 1 — pending changes are not newest-first

**Severity:** Moderate  
**Classification:** Not new in `a95afcbe`. The section-order implementation was introduced earlier in the amendment batch; the pending-list feature does not exist on `301a11fc`/`main`. D119 was recorded after `a95afcbe`, but Round 2 expressly makes it governing.

### User scenario

1. On a published day, edit a flying detail.
2. Later, edit a Ground Programme detail.
3. Open “N pending ▾” from the week or board.

### Actual

`raptor-port/src/ui/pendlist.ts:199-212` sorts exclusively by `RANK`, then original array order. Flying content ranks before Ground Programme content, so the older flying edit remains above the newer ground edit.

### Expected

Per D119, the newer ground change must appear first. Items with no edit-record time—structural actions, filings, OIL changes or “earlier” changes—belong below timed items, retaining day-section order among themselves.

### Fix

In `raptor-port/src/ui/pendlist.ts`:

1. Add a helper that returns `lastEdit(item.keys)?.t`, or `null` where the item has no attributable edit time.
2. Replace the `RANK`-only sort in `pendListHTML` with:

   - timed before untimed;
   - timed items by timestamp descending;
   - equal timestamps by original stable index;
   - untimed items by `RANK`, then original index.

3. Do not invent timestamps for D114 filing pairs or structural `logAction` rows whose record has no keyed time.

### Regression test

Add a pending-list test that:

- makes an older change in an earlier-ranked section;
- makes a newer change in a later-ranked section;
- verifies the newer line is first;
- includes an untimed request pair or filing and verifies it appears below timed changes;
- verifies two untimed items retain day-section order.

## Finding 2 — a version or parked plan can restore a second live row for one request

**Severity:** High  
**Classification:** Older. The relevant `draftSelect`, `loadVersionToWorkingCopy`, `acceptInput`, `reconcileDayFiling` and `unacceptInput` behaviour is already present on `301a11fc` and therefore on `main`. `a95afcbe` neither creates nor closes it.

### User scenario

1. Create a Meeting request covering Monday and Tuesday.
2. Accept it onto Monday.
3. Publish Monday and Tuesday.
4. Press ✕ on its Monday row.
5. Accept the same request onto Tuesday.
6. Preview Monday’s issued version, which still contains the request row, and choose “Load onto working copy”.

The same failure can be reached by switching back to a parked Monday plan containing the old row.

### Actual

`loadVersionToWorkingCopy` installs the frozen Monday day before calling `reconcileDayFiling` (`raptor-port/src/engine/drafts.ts:542-558`). The reconciler only asks whether the request has a row anywhere (`raptor-port/src/engine/slots.ts:608-619`); it does not detect that the request now has rows on both Monday and Tuesday.

The load succeeds silently and the same request appears twice.

A subsequent ✕ makes the count corruption visible:

- `unacceptInput` removes the first matching row and stops (`slots.ts:628-650`);
- the other row remains while the request is changed to `r`;
- on that other published day, the remaining row addition and `g → r` filing cannot form a valid D114 add pair;
- the day can therefore report two pending items from the broken single request state.

This violates the explicit single-landing invariant enforced by `acceptInput` at `slots.ts:435`.

### Expected

A request must have at most one live programme row. Loading or switching to content that would restore a second row should be refused without modifying either day, with wording such as:

> Cannot load this version — Bane’s Meeting is currently on Tuesday’s programme.

That follows the existing rule that loading one day must not silently move another day.

### Fix

1. In `raptor-port/src/engine/slots.ts`, add a pure helper that examines a candidate day and returns any request `src` already present on another live day.
2. In `draftSelect`, run that preflight against `t.d` before stowing or replacing the live day.
3. In `loadVersionToWorkingCopy`, run it against `snap.d` before assigning `DAYS[di]`.
4. Route other full-day restore writers through the same preflight, particularly command/Undo restoration of a day record. Refuse the whole transaction before mutation rather than deleting or moving the other day silently.
5. Have the UI caller name the request and existing day when the preflight refuses.
6. Keep `reconcileDayFiling` as the filing-state reconciler; do not use its current “exists anywhere” check as a uniqueness validator.

### Regression tests

Add two focused tests:

- **Version load:** reproduce the six steps above; assert that loading is refused, Monday stays without the row, Tuesday retains the sole row, and exactly one live ground row has that `src`.
- **Parked plan:** park a plan with the Monday row, relocate the request to Tuesday, attempt the switch, and assert the same refusal and single-row invariant.

A follow-up assertion should press ✕ on the surviving row and verify every covered published day has the correct single filing/removal item, never the orphan-row two-item result.

## Explicit negatives

- D114’s matching uses the issued row for a deletion and the live row for an addition, so row reordering does not make it inspect the wrong `src`.
- One filing entry can pair with only one content item because of `!u.inp`.
- `g → r`, `g → u`, and blank/`r → g` use the intended remove/add pairing directions.
- Filing-only changes remain separate when no matching row exists on that day.
- A request row plus an independent reorder or crew move remains multiple changes; D114 does not swallow the second act.
- Request edits that preserve the landing do not generate a spurious filing item.
- Stable request IDs keep two same-person requests separate.
- The current issued version—Original or latest AL—is consistently selected through `dayCurVerIn`.
- `alIssue` derives `diff`, `units`, and `ukinds` synchronously from the same live state.
- `retireIssued` preserves both `units` and `ukinds`.
- Scheduler/admin and member/read-only surfaces do not introduce a second counting implementation; permissions change gestures, not the count.
- Preview rendering does not publish its frozen face, and the Amendments-panel publish control remains locked while previewing.
- I found no additional defect introduced by the D114 code itself.
